      How a Large Language Model Actually Works:
      from one token to a 1 GW campus

      An LLM is a next-token probability engine built from identical blocks of matrix multiplies. This is what it computes, why it is limited by memory bandwidth when it talks and by compute when it learns, and how that turns into HBM, NVLink, 132 kW racks, liquid cooling and tens-of-megawatt swings. Basic to advanced, every number sourced, five calculators.

      Key numbers

      Eight figures carry this article; each is sourced in Sources.

      1. Training compute ≈ 6 × parameters × tokens — Llama 3 405B: 6 × 405e9 × 15.6e12 = 3.79e25 FLOP; the paper states 3.8e25. [S2]
      2. Inference ≈ 2 × active parameters per generated token — A forward pass is one third of the training cost per token. [S7]
      3. KV cache = 2 × layers × KV heads × head dim × bytes per token — Llama 3 70B: 320 KiB per token, 40 GiB at 128K context; DeepSeek-V3's MLA needs 57× less. [S2]
      4. Compute-optimal training uses about 20 tokens per parameter — Chinchilla, confirmed by the 2024 replication; small models are deliberately over-trained past it. [S5]
      5. Decode speed ≤ HBM bandwidth ÷ bytes of weights — 70B in FP8 (70 GB) on an H200 (4.8 TB/s): at most 68 tokens per second per user at batch 1. [S9]
      6. One GB200 NVL72 rack is 132 kW nominal, liquid-cooled — 72 GPUs, 13.4 TB of HBM, one 130 TB/s NVLink domain; 100k GB200 ≈ 220 MW at PUE 1.2. [S10]
      7. A frontier training run swings the site load by tens of megawatts — Llama 3 on 16K H100s: 419 unexpected interruptions in 54 days, 78% hardware. [S2]
      8. A median text prompt costs about 0.24 Wh — Google's Gemini Apps measurement, August 2025; a 1,000-token answer on a 70B model derives to about 0.27 Wh. [S18]

      In one breath: a large language model turns text into tokens, runs them through a stack of identical transformer blocks that score every token against every earlier one, and emits a probability for the next token. Training that stack on trillions of tokens costs about six floating-point operations per parameter per token; running it costs two per active parameter per generated token, and at that point the bottleneck is how fast the weights can be streamed from memory, not how fast they can be multiplied. The hardware ladder in this article is the direct consequence: the model must fit in HBM, the HBM must be fed, and the racks that do it are 132 kW and liquid-cooled.

      The one-paragraph answer

      A large language model is a machine that, given some text, produces a probability for every possible next piece of text, picks one, appends it, and repeats. Everything else — the essays, the code, the tool calls of an agent — is that single loop run thousands of times. The loop is built from one repeated unit, the transformer block, and each block is almost entirely matrix multiplication. That is why the hardware looks the way it does: dense arithmetic units fed by very fast memory, packed into racks that draw 100 kW and more.

      The shape of the machine

      Text is first cut into tokens and each token becomes a vector of a few thousand numbers (an embedding). That vector then passes through a stack of identical blocks. Llama 3 70B has 80 of them and a vector width of 8,192 [S2]. Each block does two things: attention lets every token gather information from the earlier tokens, and a feed-forward network (FFN) transforms each token on its own. Both add their result back onto the running vector, the residual stream. After the last block, the vector is converted into one score per vocabulary entry (the logits), and a sampler chooses the next token.

      The “knowledge” of the model is the set of numbers inside those matrices, the parameters. Llama 3 70B has 70 billion of them. Nothing is looked up in a database at run time. The weights were shaped, once, by predicting the next token across trillions of tokens of text.

      Two formulas that size everything

      Two approximations from the scaling-law literature [S7] carry most of this article. For a model with N parameters:

      training compute   C ≈ 6 × N × D        (D = training tokens)
inference compute  ≈ 2 × N_active per generated token

      The factor 2 is one multiply and one add per weight in the forward pass. Training adds a backward pass that costs about twice the forward pass, so 2 + 4 = 6 [S7]. As a check, Meta trained Llama 3 405B on 15.6 trillion tokens: 6 × 405e9 × 15.6e12 = 3.79e25 FLOP, against the 3.8e25 the paper states [S2]. For inference, a 70B dense model costs 2 × 70e9 = 1.4e11 FLOP per token.

      Two different limits

      Those FLOP counts say how much arithmetic is needed. They do not say how fast a GPU can do it, because the arithmetic is only half of the cost. To generate one token, a GPU must also stream every active weight from memory (HBM) to the compute units. At batch size 1 the arithmetic per byte moved is tiny, so the GPU waits on memory. Generation is therefore limited by memory bandwidth. Reading the prompt, and training, process many tokens per weight fetched, so they are limited by compute. The rest of the article is this split, worked out in numbers.

      • Talking (decode): bandwidth-bound. Tokens per second at batch 1 is at most HBM bandwidth divided by the bytes of weights. For a 70B model in FP8 on an H200 (4.8 TB/s [S9]), that is 4.8e12 / 70.6e9 ≈ 68 tokens per second, derived.
      • Reading and learning (prefill, training): compute-bound, so they scale with peak FLOP/s and with how much of it you keep busy (MFU).
      • Remembering the conversation: the KV cache grows with every token and competes with the weights for the same HBM (section 4).

      What to carry into the later sections

      Size the memory by total parameters plus the cache. Size the compute by active parameters times tokens. Size the electrical and cooling plant by the number of GPUs that those two requirements force you to rack together.

      Tokens: the unit everything is billed in

      A model never sees letters or words. A tokenizer cuts the text into pieces from a fixed vocabulary and replaces each piece with an integer ID. Common English words are usually one token; rare words, other languages and source code split into several. Price, speed and context limits are all counted in tokens, so the tokenizer decides what a page of text costs.

      2.1 What a tokenizer does

      The dominant method is byte-pair encoding (BPE). Start from the 256 possible bytes. Count which adjacent pair of symbols is most frequent in a large corpus, merge that pair into a new symbol, and repeat until the vocabulary reaches a target size V. Encoding a new string replays those merges in order. “Byte-level” BPE, used by GPT-2 onward, tiktoken, Llama 3, Qwen and DeepSeek, can encode any string, because every string is bytes and no character is ever unknown [S72].

      Two libraries recur. SentencePiece treats the input as a raw stream with whitespace written as ▁; it implements BPE and a unigram model and was used by Llama 1/2, T5 and Gemma (background, not re-read for this article). tiktoken is OpenAI’s fast BPE implementation, with encodings such as cl100k_base (GPT-4 era) and o200k_base (GPT-4o era and gpt-oss) [S72].

      2.2 Vocabulary sizes

      The vocabulary is a trade. A larger V packs more text into each token, so fewer steps are needed per document, but it enlarges the embedding table (V × d parameters) and the output layer. For Llama 3 70B that table is about 128,256 × 8,192 ≈ 1.05e9 parameters, with a similar output head, derived from the vocabulary in [S2].

      2.4 Why tokens set cost and context

      cost = input_tokens × input_price + output_tokens × output_price

      Take a 10,000-word document priced at $2 per million input tokens (the Sonnet 5.5 list price [S27]):

      • English, o200k: 10,000 × 1.20 = 12,000 tokens, $0.024.
      • Indonesian, o200k: 10,000 × 1.60 = 16,000 tokens, $0.032.
      • Indonesian, cl100k or Qwen3: 10,000 × 2.05 = 20,500 tokens, $0.041.
      • English on the 1.80 tokens-per-word Claude tokenizer: 18,018 tokens by the dossier’s 555k-word rule, $0.036.

      The same ratio applies to the context window. A window of 128K tokens holds fewer Indonesian words than English ones, in proportion to the table above. The effect compounds with the KV cache (section 4), which is also counted per token: a language that costs 1.5× the tokens also costs 1.5× the cache memory for the same document.

      Inside one block: embeddings, position, attention

      Each token ID is swapped for a vector, told where it sits in the sequence, and then passed through a stack of identical blocks. In every block, each token looks back over the earlier tokens, weighs which ones matter, and mixes their information into its own vector; a second small network then reworks that vector. The model is this block repeated, 80 times in Llama 3 70B [S2], with the same shapes at every depth. The parts are described below in the order the data meets them (see the block figure in section 1).

      3.1 Embeddings: a lookup table of meaning-vectors

      An embedding matrix E of shape V × d holds one row per vocabulary entry. Token ID 5,000 simply fetches row 5,000, a vector of d numbers (d_model, 8,192 for Llama 3 70B [S2]). The vector is the starting point for that token’s meaning, and every later layer refines it. Small models often reuse the same matrix as the output head: Qwen3 0.6B, 1.7B and 4B tie input and output embeddings [S3].

      3.2 Position: from sinusoids to million-token contexts

      Attention treats its inputs as an unordered set, so order has to be injected. Positional encoding has gone through four steps.

      • Sinusoidal (2017). A fixed pattern PE(pos,2i) = sin(pos / 10000^(2i/d)) with the matching cosine, added to the embeddings [S51].
      • RoPE. Rotary position embedding rotates each two-dimensional pair of query and key components by an angle pos × θ_i, with θ_i = base^(−2i/d). The dot product of a query and a key then depends only on their distance [S47]. RoPE is the common choice today; Llama 3 uses base 500,000 [S2].
      • ALiBi. No position vectors at all; each head subtracts a linear penalty m × |i − j| from the attention scores. A 1.3B model trained on 1,024 tokens ran at 2,048 tokens with the same perplexity as a sinusoidal model trained at 2,048, and trained 11% faster using 11% less memory [S48].
      • YaRN. Rescales the RoPE frequencies so a trained model can be extended to longer context, reported to need 10× fewer tokens and 2.5× fewer training steps than earlier extension methods [S49].

      In practice the context is grown in stages. DeepSeek-V3 is pre-trained at 4K tokens, extended to 32K, then to 128K [S1]. Llama 4 Scout is listed at 10M tokens and Maverick at 1M [S23]. DeepSeek-V4 claims 1M and swaps dense attention for a hybrid compressed-sparse scheme; at 1M it needs 27% of V3.2’s per-token FLOPs and 10% of its KV cache [S26].

      3.3 Attention, step by step

      For a sequence of n token vectors X (shape n × d), one head of attention works as follows [S51]:

      Q = X·W_Q     K = X·W_K     V = X·W_V          (each W is d × d_h)
S = Q·KT / √d_h                              (n × n scores)
S_ij = −∞  for j > i                             (causal mask)
A = softmax(S), row by row                        (each row sums to 1)
head = A·V

      The query says what a token is looking for, the key says what each earlier token offers, and the value is the content that gets averaged. The mask forbids a token from seeing the future, which is what makes next-token training legal. The softmax turns each row of scores into weights. The division by √d_h exists because, for unit-variance components, q·k has variance d_h; without scaling, the softmax saturates [S51]. With d_h = 128, the divisor is √128 = 11.3, derived.

      The cost is the catch. The score matrix is n × n, so compute grows as n² × d and a naive implementation writes n² numbers to HBM. FlashAttention computes the same exact result in tiles that stay in on-chip SRAM, never materialising the full matrix; it reported a 3× speed-up on GPT-2 at 1K context and the first better-than-chance result on the 16K-token Path-X task [S50].

      3.4 Many heads, fewer KV heads

      A layer runs h heads in parallel and concatenates them. Each head needs its own K and V during generation, and those are what the KV cache stores. Four designs reduce that load:

      • MHA: every query head has its own K/V (the original design).
      • MQA: all query heads share a single K/V head [S46].
      • GQA: g K/V groups with 1 < g < h [S45]. Llama 3 uses 8 KV heads at every size [S2]; Qwen3 MoE uses 4 [S3]. For Llama 3 70B that is 64 / 8 = 8× less cache than MHA, derived.
      • MLA (DeepSeek-V2/V3): K and V are projected down into a shared latent of 512 numbers, plus a 64-number RoPE key. Only those 576 values per layer are cached; K and V are re-expanded when needed [S1]. Full MHA with 128 heads of 128 dimensions would store 2 × 128 × 128 = 32,768 values per layer, so MLA is 32,768 / 576 ≈ 57× smaller, derived.

      3.5 The feed-forward network and the residual stream

      After attention comes the FFN, applied to each token independently. Llama-style models use a gated form, SwiGLU: FFN(x) = W_down · (SiLU(W_gate·x) ⊙ W_up·x) (background, [S2] for the model). It widens the vector to a hidden size several times d, applies a nonlinearity, and narrows it back. By parameter count it dominates: with MHA attention is about 4d² weights per layer while a gated FFN is about 3 × d × d_ff, roughly 8 to 10.5 d², so the FFN holds about two thirds of a dense block (derived). That is the part an MoE replaces (section 5).

      Both sub-layers write back with a residual add, in the pre-norm form x ← x + Sublayer(Norm(x)). The vector between blocks is the residual stream; each block edits it and none replaces it, which keeps gradients healthy through 80 layers. The normalisation is RMSNorm, x / RMS(x) × γ, which drops LayerNorm’s mean subtraction and is cheaper. DeepSeek-V3 adds extra RMSNorms after its compressed latents [S1].

      Why the maths decides the hardware

      Almost every operation above is a dense matrix multiply, which tensor cores run at near peak. Attention over a long context is the exception, because it also reads the cache. That one memory read per token is what the next section sizes.

      The KV cache: where your HBM goes

      When a model writes a reply, each new token needs the keys and values of every token before it. Recomputing them each step would be absurdly wasteful, so they are stored in GPU memory: the KV cache. It grows with every token of every conversation, and it sits in the same HBM as the weights. On a long context, the cache, not the parameter count, decides how many users one GPU can hold.

      4.1 The formula and a worked table

      KV bytes = 2 (K and V) × n_layers × n_kv_heads × d_head × bytes per value × tokens × batch

      A check against a published number: OPT-13B has 40 layers, 40 heads of 128 dimensions in 16-bit values. 2 × 5,120 × 40 × 2 = 819,200 bytes, the 800 KB per token stated in the vLLM paper [S30]. For Llama 3 70B (80 layers, 8 KV heads, d_head 128 [S2]): 2 × 80 × 8 × 128 × 2 = 327,680 bytes, which is 320 KiB per token. At 128K tokens (131,072) that is 320 KiB × 131,072 = 40 GiB, derived.

      4.2 Long context versus concurrent users

      Put the 70B model on one H200, which has 141 GB of HBM [S9]. In FP8 the weights take about 70.6 GB, leaving 141 − 70.6 = 70.4 GB for everything else. One conversation at 128K tokens needs 40 GiB (42.9 GB), which is more than half the size of the FP8 weights. Divide the remainder by the per-sequence cache and the upper bounds on concurrency, before any runtime overhead, are:

      • at 8K tokens (2.5 GiB = 2.68 GB each): 70.4 / 2.68 ≈ 26 sequences;
      • at 32K tokens (10 GiB = 10.74 GB each): 70.4 / 10.74 ≈ 6 sequences;
      • at 128K tokens: 1 sequence, with about 27 GB left.

      These are derived ceilings, not benchmarks; real engines also reserve working memory. The shape is what matters: quadrupling the context cuts the number of simultaneous users by about four.

      Waste makes it worse. The vLLM authors measured that earlier serving systems used only 20.4% to 38.2% of KV memory for real token state, with the rest lost to fragmentation and over-reservation; paging the cache like virtual memory raised throughput 2–4× [S30]. Three levers shrink the cache itself: fewer KV heads (GQA, 8× on Llama 3 70B), a compressed latent (MLA, about 57× against full MHA), and a smaller cache datatype, since the formula is linear in bytes per value.

      The datatype lever is simple arithmetic. The table assumes 16 bits per cached value. Storing the cache in 8 bits halves every figure: the 128K-token Llama 3 70B sequence drops from 40 GiB to 20 GiB (derived). The formula has no hidden constants, so any change to layers, KV heads, head size or precision scales the result in proportion; the calculator below applies exactly this formula.

      Mixture of Experts: big brain, small bill

      In a mixture-of-experts (MoE) model, the single feed-forward network of each block is replaced by many smaller ones, called experts, plus a small router. For every token the router picks a handful of experts and the rest stay idle. The model can hold far more knowledge than it computes with on any one token. The price is paid elsewhere: all experts must sit in memory, and tokens must be shipped between GPUs to reach them.

      5.1 Routing and load balancing

      DeepSeek-V3 is the best documented example [S1]. Every layer except the first three is an MoE layer with one shared expert (always on) and 256 routed experts, each with an intermediate width of 2,048. The router computes a sigmoid affinity s_i = σ(u·e_i) between the token vector u and each expert’s centroid e_i, takes the top 8, and normalises the gates over the selected experts. Each token may be routed to at most 4 nodes, which caps cross-node traffic.

      The hard part is balance. If the router favours a few experts, those GPUs saturate while others idle. Earlier MoEs such as Switch Transformers [S59] added an auxiliary loss to push the load flat; the DeepSeek authors report that a large auxiliary loss “impairs the model performance” [S1]. Their alternative is an auxiliary-loss-free bias: each expert carries a bias b_i that is added to its score only when choosing the top 8, never in the gate weights. After each training step, b_i is lowered by a small step if the expert was overloaded and raised if it was underloaded. A tiny sequence-level balance loss remains as a safety net.

      5.2 Total versus active parameters

      The result for DeepSeek-V3 is 671B total and 37B active parameters [S1], so 37 / 671 = 5.5% of the weights work on a given token (derived). Per-token compute is 2 × 37e9 = 7.4e10 FLOP, against 2 × 671e9 = 1.34e12 for a dense model of the same size, a factor of 18 (derived). Other published MoE models follow the same pattern:

Memory is set by the total: 671B parameters in FP8 is 671 GB, which fits an eight-GPU H200 server (8 × 141 = 1,128 GB, derived from [S9]) but not a single card. Compute per token is set by the active count. Bandwidth sits between them. At batch size 1, only the active experts’ weights are read per step, so decode is fast. An MoE is therefore cheapest per token at high batch and in compute, and dearest in HBM capacity.

      5.3 The network bill

      Placing different experts on different GPUs is called expert parallelism. Every MoE layer then needs an all-to-all exchange: each token’s vector is sent to the GPUs holding its chosen experts and the results are sent back. This happens twice per layer, for every layer. DeepSeek-V3’s production decode unit spans 40 nodes, 320 GPUs, with one expert per GPU plus 64 GPUs for redundant and shared experts [S1]. The cap of 4 nodes per token exists to limit exactly this traffic.

      The consequence for the facility is that an MoE service is a networking workload as much as a compute one. The experts live on NVLink within a node and on InfiniBand or RoCE between nodes, so the fabric has to be sized and cabled as part of the compute, not added afterwards. A 671B MoE is also not a “smaller” deployment than a dense 405B: the dense model needs fewer GPUs for its weights, the MoE needs fewer FLOPs per token, and which one is cheaper depends on batch size and on the interconnect.

      Operator takeaway

      Read an MoE spec sheet in two columns. Total parameters tell you how many GPUs must hold the model. Active parameters tell you what each token costs in compute. The gap between them is paid for in interconnect.

      A guessing engine: logits, softmax and sampling

      After the last block, the model produces one score for every entry in its vocabulary, 100,000 to 200,000 of them. Those scores become probabilities, and the software draws one token from them, appends it and runs the model again. Nothing is looked up or checked. Every word of every answer is a draw from a distribution the model learned during training, and the settings of that draw (temperature and its relatives) decide how adventurous the output is.

      6.1 From logits to probabilities

      The final vector h is multiplied by an output matrix to give logits, one per vocabulary entry: z = h·W_outT, a vector of length V. The softmax converts it to probabilities:

      p_i = exp(z_i / T) / Σ_j exp(z_j / T)

      T is the temperature. During training the objective is the cross-entropy L = −Σ_t log p(x_t | x_<t) averaged over tokens, and perplexity is exp(L). Minimising it is what “next-token prediction” means.

      A worked case with three candidate tokens whose logits are 4, 3 and 1 (illustrative numbers, computed here):

      6.2 Temperature, top-k, top-p, min-p, penalties

      • Greedy (T → 0): deterministic, but prone to repeating itself.
      • Temperature: a global sharpen or flatten. DeepSeek recommends T between 0.5 and 0.7, with 0.6 suggested, for R1 [S4].
      • Top-k: keep the k most probable tokens and renormalise.
      • Top-p (nucleus): keep the smallest set of tokens whose probabilities add to at least p. The set shrinks when the model is confident and widens when it is not.
      • Min-p: keep tokens with p_i ≥ min_p × p_max, a threshold that scales with the model’s confidence (Nguyen et al., arXiv 2407.01082; background reference).
      • Repetition, frequency and presence penalties: subtract from, or divide, the logits of tokens already produced. These are heuristics bolted on at serving time. They are not part of the trained model.

      The sampler runs on the final token of every step and costs almost nothing next to the matrix multiplies. Its settings are a product decision, not a hardware one, but they matter operationally: a deterministic setting makes outputs repeatable for testing, while a higher temperature raises output variety and the chance of a wrong continuation.

      6.3 Why it hallucinates

      The training objective rewards assigning high probability to text that looks like the training data. It does not reward being true. Where the training data was unambiguous, the correct continuation gets nearly all the probability. Where a fact was rare or absent, the model still has to emit some token, and it emits the most plausible-looking one. A plausible name, date or citation has the same form as a correct one. Lowering the temperature does not add knowledge; it only removes randomness around whatever the distribution already favours.

      So hallucination is not a sampler bug to be tuned away. It follows from the objective and from training data that has gaps. The practical remedies move the knowledge or the check outside the weights: retrieval of source text, tools that compute or look things up, and verifiers that test the answer (section 14 of the full article returns to this).

      6.4 Speculative decoding: guessing ahead

      Decode wastes hardware. At batch size 1 the GPU must stream all active weights from HBM to produce one token, and its arithmetic units are mostly idle. Speculative decoding uses that slack. A small draft model proposes several tokens ahead; the large model then checks all of them in one forward pass, which costs about the same as generating a single token because the weight read is shared. A modified rejection-sampling rule accepts the drafted tokens that the large model would plausibly have produced and corrects the first mismatch, so the output distribution is identical to sampling from the large model alone [S32].

      Reported speed-ups are 2–3× on T5-XXL with identical outputs [S32] and 2–2.5× on a 70B Chinchilla model [S33]. DeepSeek-V3’s multi-token-prediction module, trained to depth 1, can serve as the draft [S1]. The gain depends on how often the draft agrees with the large model, and it shrinks at large batch, where the GPU is no longer idle.

      Operator takeaway

      Speculative decoding is a way to trade spare arithmetic for fewer memory trips, with no change in answers. It helps the latency of a lightly loaded GPU and gives little on a saturated one.

      Training: from 15 trillion tokens to a base model

      Training starts with a pile of text, filtered and mixed, and a model whose weights are random. The model reads a batch, predicts every next token, measures how wrong it was, and nudges the weights to be less wrong. That step repeats millions of times, on thousands of GPUs, for weeks. The outcome is a base model that continues text well. Everything it later does as an assistant is built on top of that.

      8.1 The data pipeline and the mix

      Sources are web crawl, code, books, papers, multilingual text and synthetic data. Meta’s final Llama 3 mix was about 50% general knowledge, 25% maths and reasoning, 17% code and 8% multilingual [S2]. Processing includes deduplication at URL, document and line level, heuristic and model-based quality filters, personal-data removal, and a classifier that down-samples over-represented topics; the proportions were chosen using small-model scaling experiments [S2]. Qwen3 uses 36T tokens in 119 languages and dialects, adds text extracted from PDFs, and generates “trillions” of synthetic tokens with its maths and coding models [S3]. DeepSeek-V3 packs documents without cross-sample attention masks and trains partly with a fill-in-the-middle objective [S1].

      Public human text is finite. Villalobos et al. project that training sets will be roughly equal to the available stock of public human text between 2026 and 2032 [S41]. That window includes the present year, which is why synthetic data and reinforcement learning are now where growth is being pursued.

      8.2 Objective, optimiser, schedule, precision

      The objective is next-token cross-entropy (section 6). DeepSeek-V3 adds a multi-token-prediction loss of depth 1 [S1]. The optimiser is AdamW. DeepSeek-V3 used β₁ = 0.9, β₂ = 0.95, weight decay 0.1, a peak learning rate of 2.2e-4 after a 2K-step linear warm-up, then constant, then cosine decay, with gradient clipping at 1.0 [S1]. Llama 3 peak rates fell with size: 3e-4 (8B), 1.5e-4 (70B), 8e-5 (405B) [S2]. Kimi K2 used the Muon optimiser [S25]. The Llama 3 405B run used 16M tokens per batch at sequence length 8,192 [S2].

      The default number format is BF16. DeepSeek-V3 ran its matrix multiplies (forward, input-gradient and weight-gradient) in FP8 with fine-grained tile and block scaling, keeping sensitive operations in higher precision [S1]. DeepSeek-V4 ships its expert weights in FP4 and the remaining weights in FP8 [S26].

      8.3 Scaling laws

      Three results frame how big to train. Kaplan et al. (2020) found loss falling as a power law in parameters, L(N) = (N_c/N)^0.076, in data, L(D) = (D_c/D)^0.095, and in compute with exponent about 0.050; their allocation rule was N ∝ C^0.73, which says to grow the model much faster than the data [S7]. Hoffmann et al. (Chinchilla, 2022) fitted L(N,D) = E + A/N^α + B/D^β and concluded the opposite: for each doubling of model size, double the tokens. Their 70B model trained on 1.4T tokens, using the same compute as the 280B Gopher, reached 67.5% on MMLU [S5]. The fitted constants were E = 1.6934, A = 406.4, B = 410.7, α = 0.3392, β = 0.2849.

      A 2024 replication found that this parametric fit was inconsistent with the paper’s other two methods (it implied about 70 tokens per parameter). The re-estimate, E = 1.8172, A = 482.01, B = 2085.43, α = 0.3478, β = 0.3658, gives “around 20 tokens per parameter” [S6]. The rule of thumb that follows: with D = 20N, C = 6 × N × 20N = 120N², so N_opt = √(C/120). For Chinchilla’s budget, √(5.76e23/120) = 69B and 20 × 69B = 1.4T tokens, as published. For Llama 3 405B’s budget of 3.8e25, the rule gives 563B parameters and 11.3T tokens; Meta reports that its own data-specific fits made 405B “approximately compute-optimal” [S2]. Section 7 showed why small models ignore the rule: compute-optimal means cheapest to train, not cheapest to use.

      8.4 Parallelism

      No GPU holds a frontier model plus its training state. With mixed-precision Adam, each parameter needs 16 bytes: 2 for the weight, 2 for the gradient, 12 for the FP32 master copy and moments [S60]. For a 70B model that is 70e9 × 16 = 1.12 TB, derived, before any activations. The state is split along several axes:

      • Data parallel and ZeRO/FSDP: replicas each take a slice of the batch and all-reduce gradients; ZeRO shards optimiser state, gradients and parameters across replicas, and trained models above 100B on 400 GPUs at 15 PFLOPS [S60].
      • Tensor parallel: split each matrix across GPUs. Its traffic needs NVLink-class bandwidth, so it stays within one NVLink domain.
      • Pipeline parallel: assign consecutive layers to stages and use micro-batches to hide the idle “bubble”.
      • Context parallel: split one long sequence across GPUs.
      • Expert parallel: place experts on different GPUs, joined by all-to-all [S1].

      Llama 3 405B combined tensor, context, pipeline and fully-sharded data parallelism. On 8,192 GPUs it ran TP8 × PP16 × DP64 at 430 TFLOP/s per GPU, 43% BF16 MFU; the reported MFU range was 38–43% [S2].

      8.6 What a 16K-GPU job does to your power system

      Synchronous training makes the whole cluster compute, then communicate, in step. Meta reports that this makes power swing by “on the order of tens of megawatts” [S2]. UPS, generators and the utility interconnect must tolerate that load step; the article on xAI Colossus (150 MW in 122 days) on this site covers the other end of the scale.       Operator takeaway

      The 25.1 MW average hides the swing. Specify power quality against the step in load and its recovery after a restart, not against the mean, and treat a restart event as a normal operating condition.

      Post-training: from autocomplete to assistant to reasoner

      A freshly pre-trained model only continues text. Ask it a question and it may answer, or it may write ten more questions. Post-training turns that continuer into an assistant by showing it good answers and by scoring its attempts, and the newest recipes reward it for getting checkable answers right. The compute is a small fraction of pre-training, but the way the model now thinks, with long chains of reasoning before it answers, changes how much serving capacity you need.

      SFT, RLHF, DPO and Constitutional AI

      The first step is supervised fine-tuning (SFT): continue training with the same next-token loss as pre-training, but only on (prompt, response) pairs written or approved by people. The loss is L = −Σt log p(xt | x<t), applied to the response tokens. SFT teaches format and tone. It does not teach the model which of two plausible answers people prefer.

      That gap is closed by reinforcement learning from human feedback (RLHF). Raters rank pairs of answers, a reward model is trained to predict the ranking, and the policy is then optimised against that reward with PPO plus a KL penalty that keeps it close to the SFT model. The result that made the method standard: human raters preferred a 1.3B InstructGPT model to the 175B GPT-3, a model 135 times larger (175 / 1.3 = 135) [S52]. Alignment data bought more than parameters did.

      Direct Preference Optimization (DPO) removes the reward model and the RL loop. It solves the same objective in closed form and trains on the preference pairs as a classification loss [S53]. For an operator this matters because the job becomes an ordinary supervised run: no second model to host and no sampling loop to schedule.

      Constitutional AI replaces most human harmlessness labels with AI labels. The model critiques and revises its own outputs against a written list of principles, and AI preference judgements (RLAIF) train the final policy [S55]. Refusal behaviour is installed by these stages, which is the subject of the section on “uncensored” models further down.

      GRPO and verifiable rewards

      PPO needs a value (critic) network about as large as the policy, which roughly doubles training memory. Group Relative Policy Optimization (GRPO) drops it. For each prompt the model samples a group of G answers, scores each with a reward ri, and uses the answer's standing within the group as its advantage:

      A_i = (r_i − mean(r_1 … r_G)) / std(r_1 … r_G)

      A KL term to a reference policy remains. GRPO was introduced in DeepSeekMath 7B, which reached 51.7% on the MATH benchmark, or 60.9% when 64 samples are combined by self-consistency [S54].

      The second idea is where the reward comes from. In RL with verifiable rewards (RLVR) the reward is a program: the unit tests pass, or the final maths answer matches. No reward model is learned and none can be flattered. DeepSeek-R1 used GRPO at scale on this basis, and its authors state that reasoning ability “can be incentivized through pure reinforcement learning, obviating the need for human-labeled reasoning trajectories” [S4].

      The cost side is small by pre-training standards. Nature reported the R1 reinforcement-learning stage at $294,000 on 512 H800 GPUs for 80 hours [S73]. Those inputs give 512 × 80 = 40,960 GPU-hours, which is about $82,000 at $2 per GPU-hour. The reported figure is higher, so it evidently includes more than that single run; the composition was not verified.

      Reasoning models and test-time compute

      A reasoning model writes a long chain of thought before the visible answer. Every thinking token is generated by the same decode loop as any other token, so thinking costs tokens, time and energy in exact proportion to its length. This is the second scaling axis, test-time compute: accuracy can be bought at inference instead of at training.

      Snell et al. measured the trade. A compute-optimal allocation of test-time compute is more than 4× more efficient than best-of-N sampling, and in FLOP-matched comparisons a small model given thinking budget can beat a model 14× larger on problems it can partly solve [S57]. Verifiers, such as process reward models or unit tests, rank or prune the candidates.

      Vendors now expose this as a dial. OpenAI's gpt-oss offers low, medium and high reasoning effort, and its SWE-bench score rises from 47.9 to 52.6 to 62.4 across the three settings [S24]. The Claude API exposes an “effort” control and adaptive thinking [S27].

      The data-center consequence follows from the energy per token covered in the serving section. At roughly 1 J per generated token (an illustrative figure derived there, not a measurement), a 10,000-token reasoning chain costs about 10 kJ, which is 10,000 / 3,600 = 2.8 Wh, against about 0.27 Wh for a 1,000-token answer. Reasoning moves cost from the training cluster to the serving fleet, which is why test-time compute is a capacity-planning question and not only a benchmark one.

      Plan serving capacity for thinking tokens

      Output length, not prompt length, sets the decode load of a reasoning workload. When a product turns on a higher effort setting, the same number of requests can consume several times the GPU-seconds. Measure tokens generated per request in production before you size the next cluster.

      Distillation, fine-tuning and quantization: making it small

      A frontier model is too large and too slow for most jobs, so the field has three ways to shrink one. Distillation trains a small model to imitate a big one. Fine-tuning with LoRA adapts a model by training a sliver of extra weights instead of all of them. Quantization stores each weight in fewer bits. All three exist for the same reason you size a cooling plant to the load rather than the nameplate: memory and bandwidth are the scarce resources, and every byte removed from the weights is a byte the GPU does not have to read for every token.

      Distillation: a small student learns from a large teacher

      Distillation comes in two forms. In logit (soft-label) distillation the student is trained to match the teacher's full next-token distribution, by minimising KL(pteacher ∥ pstudent) at temperature T and scaling the loss by T² [S56]. This needs the teacher's logits. In sequence-level distillation the teacher writes text and the student is fine-tuned on it with plain SFT, so only the teacher's outputs are needed. That is the form behind the DeepSeek-R1-Distill models, which were trained on samples generated by R1 and built on Qwen2.5 and Llama 3 bases [S4]. The dossier could not re-verify the size of the training set (reported as 800,000 samples, unverified).

      LoRA and QLoRA: the maths and the memory

      LoRA freezes a weight matrix W of shape d_out × d_in and learns a low-rank update ΔW = B·A, with B of shape d_out × r, A of shape r × d_in and r far smaller than either dimension, scaled by α/r. Trainable parameters per adapted matrix are r·(d_in + d_out). On GPT-3 175B this gave 10,000× fewer trainable parameters and 3× less GPU memory than full Adam fine-tuning, and no extra inference latency once the update is merged into W [S34].

      A worked case: Llama 3 8B, rank 16, adapting all seven linear layers in each block (q, k, v, o, gate, up, down), with d = 4,096, key/value width 1,024, FFN width 14,336 and 32 layers (derived from the public model configuration; the FFN width was not re-read for this article):

      per layer = 16 × [(4096+4096) + 2×(4096+1024) + (4096+4096) + 3×(4096+14336)]
          = 16 × 81,920 = 1,310,720
total     = 1,310,720 × 32 = 41.9 M  (0.52% of 8.03 B)

      QLoRA keeps the frozen base in 4-bit NormalFloat (NF4) with double quantization of the scale constants and uses paged optimizers to ride out memory spikes. It fine-tunes a 65B model on a single 48 GB GPU while preserving 16-bit fine-tuning quality, and its Guanaco model reached 99.3% of ChatGPT on the Vicuna benchmark after 24 hours on one GPU [S35].

      The memory rules, with ZeRO's 16 bytes per parameter for mixed-precision Adam as the full fine-tune baseline (2 weights + 2 gradients + 12 for the FP32 master copy and moments) [S60]:

      • Full fine-tune ≈ 16 B/param + activations: 8B → 128 GB; 70B → 70.6 × 16 = 1.13 TB; 405B → 6.5 TB (derived).
      • LoRA (BF16 base) ≈ 2 B/param for the base + 16 B per trainable parameter + activations.
      • QLoRA ≈ 0.516 B/param for the base (4.127 bits) + 16 B per trainable parameter + activations: 8B → 4.1 GB; 70B → 36 GB (derived).

      Activations depend on sequence length and batch size, and gradient checkpointing trades extra compute for lower memory, so treat these as floors. The calculator below applies them.

      Quantization: fewer bits per weight

      Quantization stores weights as low-bit integers or small floats, with a scale per block. Memory is N × bits / 8. Four methods carry most of the field:

      • LLM.int8() halves inference memory with no degradation by keeping the few outlier dimensions in 16-bit; more than 99.9% of values are still multiplied in 8-bit [S38].
      • GPTQ is a one-shot, second-order method for 3–4 bits. It quantizes a 175B model in about 4 GPU-hours with negligible accuracy loss [S36].
      • AWQ protects the roughly 1% of weights that matter most, chosen by activation magnitude rather than weight magnitude; its TinyChat engine runs more than 3× faster than Hugging Face FP16 [S37].
      • FP8 and FP4 are hardware formats: FP8 on Hopper, Blackwell and MI355X, and NVFP4 or MXFP4 on Blackwell and MI355X [S10][S13]. gpt-oss ships its expert weights in MXFP4 so that 117B parameters fit on one 80 GB GPU [S24].

      “Uncensored” models: what abliteration actually is

      Chat models are trained to decline some requests. When a model's weights are public, that trained behaviour is part of the file, and researchers have shown it can be located and changed. The result is what people call an “uncensored” or “abliterated” model. This section describes the mechanism that was published, what it does and does not change, and where responsibility sits when such a model is hosted. It gives no procedure.

      How refusal is trained in

      Refusal is not a filter bolted on after the model. It is learned in the stages described earlier: supervised examples of declining, preference training that rewards declining in the right cases, and, in Constitutional AI, written principles the model applies to its own outputs [S52][S55]. Because it is learned behaviour stored in the weights, anyone holding the weights can change it.

      The single-direction finding

      Arditi et al. (NeurIPS 2024) reported that refusal “is mediated by a one-dimensional subspace, across 13 popular open-source chat models up to 72B” [S40]. Their approach is interpretability work: compare the model's internal activations, in the residual stream, on prompts it refuses against prompts it answers. The difference of the two mean activations defines a direction, which they call the refusal direction. Two interventions follow from it:

      • Directional ablation removes that component from every residual activation while the model runs.
      • Weight orthogonalisation edits the weights so that they never write along that direction. This is the technique the community calls abliteration.

      The converse also holds in the paper: adding the direction makes a model refuse harmless requests [S40]. A second, coarser route exists: supervised fine-tuning on data that contains no refusals has a similar effect and can degrade other behaviours; the sources here do not quantify that degradation.

      What it does and does not change

      The paper measured the effect on the behaviour and on general capability [S40]:

      Two points matter for anyone evaluating such a model. First, the edit removes a learned behaviour; it adds no knowledge and no capability. The model's factual errors and its tendency to hallucinate are unchanged. Second, the effect differs between model families by a wide margin, as the two attack-success ranges show, so a claim made about one model does not transfer to another.

      The authors addressed the dual-use question in their own ethics statement. They write that the method “marginally lowers the bar for jailbreaking open-source model weights”, and argue it “does not substantially alter the risk profile of open sourcing models”, because fine-tuning already achieved the same end [S40]. Readers can weigh that argument for themselves; it is the researchers' position, not a settled one.

      Serving: how one GPU talks to a thousand users

      Answering a prompt happens in two phases. First the GPU reads the whole prompt at once, which is heavy arithmetic. Then it writes the answer one token at a time, and each token requires reading all of the model's weights from memory again, which is a memory-speed problem and not an arithmetic one. Serving software exists to keep many users' requests in flight at once so that every one of those expensive weight reads is shared. The data-center consequence is that tokens per second per GPU is set by HBM bandwidth and by how much memory the KV cache leaves free.

      Prefill and decode

      Prefill processes the prompt in one parallel pass. It costs 2·N·n_prompt FLOPs, it is compute-bound, and it fills the KV cache. Decode then generates one token per step per sequence. Each step reads all the weights plus the sequence's KV cache for a tiny amount of arithmetic, so decode is memory-bandwidth-bound.

      Prefill example (derived): a 4,000-token prompt on a 70B FP8 model costs 2 × 70.6e9 × 4,000 = 5.65e14 FLOP. At 50% of an H200's 1,979 TFLOP/s FP8 dense peak (the 50% is an assumption) that is 5.65e14 / 9.9e14 = 0.57 s [S9].

      The metrics

      • TTFT (time to first token) ≈ queueing + prefill time.
      • TPOT / ITL (time per output token, or inter-token latency) = the decode step time.
      • Throughput = total tokens per second per GPU or per node.
      • Goodput = requests per second that meet both the TTFT and TPOT targets. DistServe reports serving “7.4x more requests or 12.6x tighter SLO” by separating the phases [S44].

      The engines

      vLLM stores the KV cache in fixed-size blocks, like operating-system pages (PagedAttention), so memory is allocated on demand and blocks can be shared between requests. Earlier systems used only 20.4–38.2% of their KV memory for real token state; vLLM reports near-zero waste and 2–4× the throughput at the same latency versus FasterTransformer and Orca [S30]. SGLang keeps a radix tree of cached prefixes (RadixAttention) to reuse KV across calls and reports up to 6.4× throughput on agent, JSON, RAG and multi-turn workloads [S31]. TensorRT-LLM is NVIDIA's compiled engine with in-flight batching and FP8/FP4 kernels (background; its documentation was not re-read for this article). llama.cpp and Ollama run GGUF-quantised weights on CPU, Apple Metal, CUDA and ROCm [S39].

      Continuous batching, prefix caching, disaggregation

      • Continuous batching: finished sequences leave and new ones join at every decode step, rather than waiting for a whole batch to finish. vLLM and SGLang both do this [S30][S31].
      • Prefix caching: reuse the KV cache for a shared system prompt or document. API vendors price cache reads at 2.5–10% of normal input [S27].
      • Disaggregated prefill and decode: run the two phases on separate GPU pools and move the KV cache between them over NVLink or RDMA [S44][S63]. DeepSeek runs a 320-GPU decode unit [S1]. vLLM's own documentation is explicit that it lets you tune TTFT and ITL separately and control tail ITL, but that it “DOES NOT improve throughput” [S63].

      Size by memory first, then by batch

      For decode, divide HBM bandwidth by weight bytes to find the ceiling, then check how many sequences' KV caches fit beside the weights. That second number, not the FLOP rating, sets your tokens per second per kW. Prefix caching and a tighter context limit raise it without new hardware.

      The hardware ladder, rung by rung

      The same model runs on a laptop, a workstation card, a server, a liquid-cooled rack or a campus of tens of thousands of accelerators. What changes from rung to rung is memory, memory bandwidth and the power and cooling needed to feed them. The model that fits a rung is set by its weight memory plus its KV cache, and the speed is set by bandwidth. For a facility engineer the important step is the one from server to rack, where air cooling stops being an option.

      The serving rule used throughout: memory needed = weights (N × bytes per parameter) + KV cache (see the KV-cache section and its calculator) + roughly 10–20% runtime overhead (a rule of thumb, not a sourced figure). Training needs about 16 B per parameter plus activations [S60]; the energy calculator in the training section turns a GPU count into megawatts.

      Agents and harnesses

      A model on its own only produces text. An agent is that model placed inside a loop: it proposes an action, ordinary software carries the action out and reports the result, and the model decides what to do next. The software around the model is the harness, and it, not the model, decides what is allowed to run, what gets checked and when to stop. For an operations team the practical point is that an agent turns one question into dozens of model calls, so cost, latency and security all multiply.

      Tool calling, ReAct, workflows and agents

      In tool calling the model emits a structured request, typically JSON with a function name and arguments. The harness executes it and returns the result as a new message. The model never runs code itself. ReAct showed the value of interleaving reasoning, action and observation: on the ALFWorld and WebShop tasks it beat imitation and reinforcement-learning methods by 34 and 10 absolute points, using one or two in-context examples [S42].

      Anthropic's guidance draws a line that is useful for scoping: “Workflows are systems where LLMs and tools are orchestrated through predefined code paths. Agents are systems where LLMs dynamically direct their own processes and tool usage.” Its patterns are prompt chaining, routing, parallelisation, orchestrator-workers and evaluator-optimiser, and its advice is to start simple and to design the agent-computer interface as carefully as a human interface [S62]. A fixed workflow is cheaper and easier to test; reach for an agent only when the steps cannot be known in advance.

      The Model Context Protocol

      MCP standardises how a model application connects to tools. It uses JSON-RPC 2.0 between hosts (the LLM application), clients (connectors) and servers. Servers expose resources, prompts and tools, and clients may offer elicitation, where the server asks the user for input. The version read for this article is the 2026-07-28 revision. Its security principles are user consent and control, data privacy and tool safety. It states that tools “represent arbitrary code execution” and that tool descriptions are to be treated as untrusted unless the server is trusted [S61].

      Designing the harness

      The model proposes; the harness disposes. A working checklist, drawn from the vendor guidance cited above [S61][S62]:

      • Context. Keep a small, clear set of tools with explicit schemas. Manage the window with summarisation or compaction, give sub-agents their own windows, and cache the stable prefix. Memory is the window itself, a retrieval store, or notes persisted to files.
      • Verification. Check results with tests, linters or an evaluator, not with the model that wrote them. A model grading itself shares its own blind spots.
      • Sandbox. Run tools in a container with no secrets and controlled network egress.
      • Budgets. Cap steps, tokens and wall-clock time.
      • Approval. Require a human to confirm irreversible actions.
      • Logging. Record every call so a run can be replayed.

      Multi-agent designs, in which an orchestrator hands separable subtasks to parallel workers, spend tokens in proportion to the number of agents. Anthropic's advice is that this pays only when the subtasks are genuinely independent [S62].

      Failure modes

      • Hallucination. The sampler always produces some plausible continuation, so claims must be checked by tools or retrieval.
      • Prompt injection. Instructions hidden in a web page, file or tool output can redirect the agent. MCP's specification treats tool descriptions as untrusted [S61]. Mitigations are least-privilege tools, human confirmation and isolating untrusted content.
      • Loops and drift. The agent repeats a call or forgets the goal. Step and token budgets and progress checks contain it.
      • Over-trust in self-verification. Use external checks, such as test suites.

      Treat every tool result as hostile input

      Give an agent the fewest tools and the least privilege that finish the job, run them in a sandbox without secrets, and require a person to approve anything irreversible. If an agent can read a web page and also run a command, a hidden instruction on the page can run the command.

      The frontier and its limits

      The largest training runs have grown by about five times a year, and the people building them are now meeting three limits: the supply of human-written text, the cost of electricity and the physical size of a single site. The growth is shifting from bigger pre-training runs towards two other levers, reinforcement learning on checkable tasks and more thinking at answer time. All of these end up as megawatts, which is why this is a facilities topic and not only a research one.

      Compute grows about five times a year

      Epoch AI's dashboard puts frontier language-model training compute at roughly 5× per year since 2020, training cost at about 3.5× per year, and chip price-performance improving about 49% per year since 2023 [S64].       The data wall and synthetic data

      Villalobos et al. projected that, if trends continue, models will be trained on datasets “roughly equal in size to the available stock of public human text data between 2026 and 2032” [S41]. 2026 is the start of that window. The responses already in use are synthetic data (Qwen3 used “trillions” of synthetic tokens), reinforcement learning on tasks whose answers can be verified, and distillation from stronger models [S3][S4]. Each of these moves compute out of the pre-training run and into data generation and post-training.

      Test-time compute as the new axis

      The scaling laws that guided pre-training have a counterpart at inference: accuracy rises with the number of thinking tokens [S57][S24]. This moves cost from the training cluster to the serving fleet. Training is a project with an end date; thinking tokens are a recurring load that grows with usage and with the effort setting, so it adds permanent data-center capacity.

      Energy: per query, per run, per grid

      • Per query. Google reports that the median Gemini Apps text prompt uses 0.24 Wh, emits 0.03 gCO2e and consumes 0.26 mL of water, with energy per prompt down 33× in twelve months (August 2025) [S18]. Epoch estimates about 0.3 Wh for a typical GPT-4o query, against an older claim of 3 Wh [S66]. Because energy follows tokens, a long reasoning or agent run can cost one to two orders of magnitude more (derived from the serving section; not measured).
      • Per run. Epoch's power estimates in the table above run from about 22.6 MW for Llama 3.1 405B to about 233 MW for GPT-6 Astra. The worked 70B budget earlier in this article gives 25.1 MW on 16,384 GPUs, consistent with the Llama 3 estimate.
      • Per grid. The IEA estimates data centres used about 415 TWh in 2024, around 1.5% of world electricity, and projects about 945 TWh in 2030 (an increase of 945 / 415 = 2.3×); the United States accounts for 45% of the 2024 use [S67].
      • Scale illustration (derived). One billion prompts a day at 0.24 Wh is 240 MWh a day, which is 240 / 24 = 10 MW on average.

      Open and closed models

      Open-weight frontier-scale mixture-of-experts models now exist under MIT or Apache licences: DeepSeek-V4-Pro at 1.6 trillion parameters, Kimi K2 at 1 trillion, Qwen3 and gpt-oss [S26][S25][S3][S24]. Closed models from Anthropic, OpenAI and Google do not disclose their sizes [S27][S28][S29]. On the official SWE-bench board the best entries are close (79.2 against 78.8), though the second entry is a vendor agent built around Doubao-Seed-Code, whose weights may not be open, which is unverified [S22]. For an operator the practical difference is who carries the serving cost: with open weights you can run the model on your own racks and you carry the hardware sizing described in the earlier sections.

      Plan for serving growth, not only for a training run

      A single frontier training run is estimated at 233 MW, but the load that keeps growing is inference: every higher effort setting, every agent step and every extra user adds tokens. At 0.24–0.3 Wh per ordinary prompt the energy is small per query and large in aggregate, so capacity plans should carry tokens per day as a first-class input.

      Frequently asked questions

      Does an LLM calculate, or does it guess?

      It computes a probability over the next token and samples from it; that is the whole mechanism. Arithmetic, facts and plans all come out of that distribution, which is why the output is always plausible and not always right. Reasoning models spend extra compute at answer time to improve the odds, and interpretability work shows real internal circuits, but nothing in the sampler checks truth. In an operations setting every number an LLM produces is a proposal that a deterministic tool must verify.

      How much GPU memory does a model need?

      Weights take parameters × bytes per parameter (70B at BF16 = 140 GB, at FP8 = 70 GB, at 4-bit about 35 GB), plus the KV cache, which grows with context and concurrent users: 2 × layers × KV heads × head dimension × bytes per token, 320 KiB per token for Llama 3 70B, so 40 GiB for one 128K-token session. The fit calculator in this article does the sum for any model and hardware.

      Why is text generation limited by memory bandwidth and not by FLOPs?

      Each generated token needs every weight read from HBM once, but only a few operations per weight. At batch 1 the arithmetic intensity is far below the GPU's ridge point, so the roofline is the bandwidth line: 70B in FP8 on an H200 cannot exceed 4.8 TB/s ÷ 70 GB = 68 tokens per second per user. Batching users together raises the intensity until compute becomes the limit.

      What does an AI training run do to a data center?

      Llama 3 ran on up to 16,384 H100s at 700 W each; Meta reports power swings on the order of tens of megawatts as jobs start, checkpoint and restart, and 419 unexpected interruptions in a 54-day window, 78% of them hardware. The racks that replaced that generation, GB200 NVL72, draw 132 kW nominal and are liquid-cooled, which is why direct-to-chip cooling, transient-tolerant electrical design and PUE at high density are now the plant-room questions.

      RAG, a long context window, or fine-tuning: which one?

      Facts that change often or are private: retrieval (RAG), which is fresh, citable and cheap to update. One large document set per session under about a million tokens: a long context with prompt caching. A behaviour, format, tone or narrow skill: a LoRA fine-tune, which changes how the model answers rather than what it knows. The article's section on agents gives the decision table with the costs.

      How much energy does one prompt use?

      Google measured the median Gemini Apps text prompt at 0.24 Wh, 0.03 gCO2e and 0.26 mL of water in August 2025. The article's serving section derives about 1 joule per token for a 70B model on an H200 at batch 32, which is roughly 0.27 Wh for a 1,000-token answer, the same order as Google's figure and Epoch's 0.3 Wh estimate for a GPT-4o query.

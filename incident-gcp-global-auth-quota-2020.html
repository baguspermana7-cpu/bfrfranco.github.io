Google Global Authentication Outage — User ID Service Quota Collapse (Dec 14, 2020)

Google Cloud 2020-12-14 47m core impact Software

On December 14, 2020, an automated quota-management system wrongly cut capacity on the account database behind Google's central User ID Service to near-zero. An October change had registered that service with a new quota system while leaving parts of the old one in place; the residual system reported the service's usage as 0, which triggered the automated reduction. With the quota starved, the Paxos leader could no longer write, so credential issuance and account-metadata lookups failed for every Google account. Any request needing OAuth-based authentication returned errors, taking down Gmail, YouTube, Drive, Docs, Calendar, Play, Google Cloud, Workspace and even Google Home speakers globally. Engineers identified the root cause about 22 minutes after onset and mitigated by disabling quota enforcement datacenter by datacenter; the authentication core recovered in 47 minutes (03:46–04:33 US/Pacific).

Root cause

TRIGGER (latent misconfiguration, October 2020): Per Google Cloud incident report #20013, the originating fault was an incomplete quota-system migration. As part of an ongoing migration of the User ID Service to a new quota system, a change was made in October 2020 to register the User ID Service with the new quota system, but parts of the previous quota system were left in place, which incorrectly reported the User ID Service's usage as 0. The User ID Service maintains a unique identifier for every account and handles authentication credentials for OAuth tokens and cookies, so this seeded a dormant, incorrect quota-accounting state for a globally critical service while everything continued to function normally.\n\nWHY IT STAYED DORMANT (grace period): An existing grace period on enforcing quota restrictions delayed the impact. It masked the zero-usage misconfiguration from roughly October until December 14 (about two months), during which automation saw usage reported as 0 but did not act on it, so operators had no clear signal anything was wrong.\n\nWHY SAFEGUARDS DID NOT CATCH IT: When the grace period expired, it triggered the automated quota systems to decrease the quota allowed for the User ID Service. The safety checks that should have prevented lowering quota below actual usage failed because they did not cover the scenario of zero reported load for a single service — they accepted the reported zero as legitimate and allowed the automated reduction to proceed.\n\nMECHANISM / PROPAGATION: As a result, the quota for the account database was reduced, which prevented the Paxos leader from writing. Shortly after, the majority of read operations became outdated (stale), which resulted in errors on authentication lookups. Because the User ID Service issues OAuth tokens and cookies for every Google account, credential issuance and account-metadata lookups failed globally beginning around 03:46 US/Pacific on December 14, 2020.\n\nBLAST RADIUS: The failure was global across both Google Cloud Platform and Google Workspace because authentication is a shared dependency. Reported service impact included BigQuery streaming requests at ~75% errors (and BigQuery jobs ~10%), ~15% of Cloud Storage requests impacted, and ~4% of GKE control-plane API requests failing. This is the same event as the widely reported ~45-minute global Google/Gmail/YouTube outage of December 14, 2020.\n\nESCALATION AND RECOVERY: Automated alerts detected capacity issues at 03:43; Google engineers were paged at 03:48 ('within one minute of customer impact' per the report); root cause and a potential fix were identified at 04:08. Recovery was achieved by disabling quota enforcement (the offending automated control), not a physical failover: enforcement was disabled in one datacenter at 04:22, applied globally by 04:27, and error rates returned to normal by 04:33. Some services, including Google Calendar and the Google Workspace Admin Console, served errors up to 05:21 due to a traffic spike following initial recovery. There is no physical-redundancy dimension here; the relevant resilience factor was the Paxos-replicated account database, whose consistency model is why a blocked leader plus stale reads produced authentication errors rather than mere degradation.

Contributing factors

  • Incomplete quota-system migration (October 2020): the User ID Service was registered with the new quota system while parts of the previous quota system were left in place and incorrectly reported the service's usage as 0 — a latent misconfiguration seeded roughly two months before the outage.
  • Grace-period masking: an existing grace period on enforcing quota restrictions delayed and hid the impact until it expired, so the zero-usage fault produced no operator-visible symptom until automation acted on it.
  • Inadequate safety checks: the checks failed because they did not cover the scenario of zero reported load for a single service, so an obviously anomalous 'zero usage' signal for a globally critical service was accepted and did not block the automated quota reduction.
  • Automated global quota reduction with no effective guard: grace-period expiry triggered the automated quota systems to decrease the quota for the User ID Service / account database without a check that would treat lowering quota below real usage as an anomaly.
  • Tight coupling of a single control-plane dependency to the entire data plane: because the User ID Service issues OAuth tokens and cookies for every account, a quota fault in one service cascaded into a global authentication failure across both GCP and Workspace.
  • Consistency-model sensitivity: reducing the account-database quota prevented the Paxos leader from writing, after which the replicated store served stale reads, converting a capacity shortfall directly into authentication-lookup errors.

Correction of errors (COE)

  • Add sanity floors / guardrails so the automated quota system cannot reduce capacity of a critical service to near-zero based on an implausible reading (e.g. usage reported as 0). Google identity / quota-platform engineering · Directionally indicated by postmortem (not itemized verbatim in ledger)
  • Complete and verify quota-system migrations so no residual legacy system can misreport usage for a service registered with the new system. Google identity / quota-platform engineering · Directionally indicated by postmortem
  • Improve resilience to write failures in the account database so a blocked Paxos leader / quota denial does not immediately halt credential issuance globally (graceful degradation / write fallback). Google account-database / Paxos team · Official remediation item on write-failure resilience (implies no graceful fallback existed at the time)
  • Retain and formalize the datacenter-by-datacenter quota-enforcement-disable procedure as a tested emergency mitigation runbook. Google SRE / incident response · Demonstrated effective during this incident (one-DC then all-DC)

Lessons learnt

  • A shared identity/authentication layer is the highest-leverage single point of failure in a large platform: when it fails, cloud, consumer web, and IoT hardware all fall at once, worldwide.
  • Automation acting on an implausible input (usage = 0) can inflict global damage in minutes; critical-service automation needs sanity bounds and confirmation before enforcing drastic reductions.
  • Migrations that leave the old system partially active create silent inconsistency; a registration change is not complete until every legacy path stops observing and acting on the service.
  • Fast root-cause identification (~22 min here) is what kept a maximal-blast-radius outage to under an hour — observability and clear alerting materially bounded the impact.
  • Strong consistency (Paxos writes) with no graceful degradation means a control-plane denial (quota) can fully stop the data plane; critical write paths need a resilience story for admission/quota failures.
  • A simple, well-scoped mitigation lever (disable quota enforcement, DC by DC) can recover a global outage quickly when the root cause is understood — such levers should be pre-built and rehearsed.

Improvements & remediation

  • Introduce hard guardrails preventing automated near-zero quota reductions on tier-0 services, with mandatory sanity checks against historical baselines.
  • Enforce migration-completeness gates so a service cannot be dual-observed by an old and a new quota system simultaneously.
  • Add graceful-degradation / write-fallback paths for the account database so credential issuance can survive a Paxos-write or quota denial without total global failure.
  • Instrument and alert on quota-vs-actual-usage divergence for critical services to catch a zero-usage misreport before it drives enforcement.
  • Pre-stage and regularly drill the DC-by-DC quota-enforcement-disable runbook so the ~41-minute onset-to-global-mitigation window can be compressed further.
  • Reduce identity-layer blast radius through isolation or partial-availability modes so a single account-database fault does not simultaneously black out every product surface.

Comprehensive analysis

Failure mechanism — how a migration remnant zeroed a global service

The proximate trigger was not a hardware fault or traffic spike but a latent inconsistency from an incomplete migration. When the User ID Service was registered with a new quota system in October, parts of the old quota system were left running and continued to observe the service — reporting its usage as 0. Weeks later, that stale zero was treated as ground truth by automation, which reduced the account-database quota accordingly. The system was, in effect, told that a service carrying global authentication load was doing no work, and it sized capacity to match.

Why it cascaded globally

The reduced quota prevented the Paxos leader from writing, which halted credential issuance and account-metadata lookups for every Google account. Because virtually all Google products authenticate through this shared identity layer via OAuth, a single control-plane action propagated into widespread 5xx errors across independent product families at once: GCP (Console, Storage, BigQuery, GKE), Workspace (Gmail, Calendar, Meet, Docs, Drive), consumer services (YouTube, Play), and even Google Home smart speakers. The blast radius reflects architecture, not coincidence — one account database is the common dependency, so its failure is simultaneously everyone's failure.

Detection and recovery

Automated capacity alerts fired at 03:43 US/Pacific, errors began at 03:46, and engineers were paged at 03:48. Root cause was identified by 04:08 — roughly 22 minutes after onset — which is the decisive fact in keeping this under an hour. Mitigation was surgical: disable quota enforcement in one datacenter at 04:22 to confirm the fix, then roll it to all datacenters by 04:27, with error rates normalizing at 04:33. The Pacific-time sequence converts cleanly to UTC (PST = UTC-8: 03:43→11:43 alerts, 03:46→11:46 impact, 04:22→12:22 one-DC, 04:27→12:27 all-DC, 04:33→12:33 restored), and Wikipedia's independently reported UTC window (~11:45 start, ~12:33 restore, ~50 minutes) corroborates the same events, confirming the timeline's internal consistency.

Organizational and systemic factors

Three systemic conditions turned a config remnant into a global outage: automation empowered to enforce drastic capacity changes without a sanity floor; a migration process that allowed old and new quota systems to coexist and disagree; and a strongly-consistent write path (Paxos) with no graceful degradation when admission/quota was denied — a failover could not help because cluster-wide denial starved every replica's writes (inference, flagged). The official remediation emphasis on write-failure resilience implies no write fallback existed at the time.

Cross-incident pattern

This incident is a canonical shared-control-plane / identity-SPOF failure: a small, automated, seemingly-safe change in a central dependency produces disproportionate, correlated, cross-product impact. The pattern recurs across large providers — automation acting confidently on bad or stale metadata, an incomplete migration leaving inconsistent state, and a single foundational service (identity, DNS, config, or routing) whose failure defeats otherwise-independent redundancy. The mitigating counter-pattern is also visible here: fast, clear root-causing plus a pre-scoped kill-switch (disable enforcement) bounded the damage to 47 minutes.

Technical deep-dive

The account data backing the User ID Service is stored in a Paxos-replicated database: a consensus group in which a leader commits writes and replicas serve reads, so consistency depends on the leader being able to commit and on replicas staying current with the committed log.\n\nThe failure chain is a quota-driven capacity starvation of this consensus system. During the October 2020 migration the service was effectively double-registered — added to the new quota system while parts of the old quota system remained active and reported its usage as 0. Quota automation sizes and enforces capacity from reported usage, so a usage of 0 signals that the service needs essentially no capacity. An existing grace period on enforcing quota restrictions suppressed action, leaving the wrong signal latent for about two months.\n\nWhen the grace period expired on December 14, the automated quota systems acted on the zero-usage figure and decreased the quota allowed for the User ID Service; the safety checks did not cover the scenario of zero reported load for a single service, so nothing blocked lowering quota below actual usage. As a result the quota for the account database was reduced, which prevented the Paxos leader from writing. Once writes stopped committing, the majority of read operations became outdated (stale). Authentication lookups depend on current account state — the service issues OAuth tokens and cookies and resolves account metadata — so stale/failed reads surfaced directly as errors on authentication lookups. Downstream services degraded in proportion to how hard they lean on fresh credential/identity checks (BigQuery streaming ~75% errors and jobs ~10%, Cloud Storage ~15%, GKE control plane ~4%).\n\nMitigation matched the mechanism: rather than restoring the database, engineers disabled quota enforcement so the artificially low quota would stop throttling the account database, restoring write capacity to the Paxos leader; reads became current again and authentication recovered. Enforcement was disabled in one datacenter at 04:22, extended globally by 04:27, and error rates normalized by 04:33, with a residual error tail on some services (e.g., Google Calendar, Workspace Admin Console) until 05:21 caused by a post-recovery traffic spike.

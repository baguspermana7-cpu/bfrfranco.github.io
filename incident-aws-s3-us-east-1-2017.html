AWS S3 US-EAST-1 Service Disruption

Amazon Web Services 2017-02-28 4h 35m core impact Human errorSoftware

An authorized S3 engineer running an established capacity-removal playbook mistyped one input; the command removed far more servers than intended, taking down the S3 index and placement subsystems in US-EAST-1. Because a very large number of services (and AWS's own status dashboard) depend on S3, the ~4.5-hour disruption cascaded across a large fraction of the internet.

Sequence of events (SOE)

  • 2017-02-28 09:37 PSTTrigger Authorized S3 team member executes an established playbook command to remove a small number of billing-subsystem servers; one input is entered incorrectly, removing a larger server set than intended.
  • 2017-02-28 ~09:37 PSTEscalation The removed capacity crosses a threshold that forces a FULL restart of two core S3 subsystems: the index subsystem (metadata/location of every US-EAST-1 object, on the read path) and the placement subsystem (allocates storage for new objects, on the write path).
  • 2017-02-28 ~09:44 PSTImpact S3 GET/LIST/HEAD/PUT/DELETE/POST APIs return elevated errors region-wide; because the index subsystem serves every request, reads fail even though object data is intact.
  • 2017-02-28 ~10:00 PSTCascade Downstream AWS services that depend on S3 in US-EAST-1 degrade: new EC2 instance launches, EBS volumes, and AWS Lambda; thousands of third-party sites/services relying on S3 fail or slow.
  • 2017-02-28 ~10:00 PSTComms failure The AWS Service Health Dashboard cannot render red status — its own control plane depends on S3 US-EAST-1 — so AWS posts status via the dashboard banner text and @AWSCloud on Twitter.
  • 2017-02-28 12:26 PSTRecovery Placement subsystem recovers; PUT/write path begins to restore for new objects as the index subsystem catches up.
  • 2017-02-28 13:18 PSTRecovery Index subsystem restart + metadata integrity checks complete enough to resume; retrieval operations start returning to normal.
  • 2017-02-28 13:54 PSTRestored S3 GET/LIST/HEAD (read) operations fully recovered — 4h17m after onset.
  • 2017-02-28 14:12 PSTRestored S3 PUT/DELETE/POST (write) operations fully recovered — 4h35m after onset; region operating normally.

Root cause

Human input error during a routine, authorized capacity-removal operation: a typo in one command argument removed a much larger set of servers than intended. The affected servers supported two S3 subsystems (index and placement) that then required a full restart. These subsystems had not been completely restarted for many years and had grown large, so the safety checks, metadata re-validation, and restart took far longer than expected — turning a capacity change into a multi-hour regional outage.

Contributing factors

  • Capacity-removal tooling allowed removing too much capacity too quickly, with no floor on minimum required capacity for a subsystem.
  • Index and placement subsystems had not been fully restarted in years and had scaled up substantially, making cold restart slow and risky.
  • Broad, hidden dependency of many AWS services on S3 in a single region turned a storage fault into a wide cascade.
  • The AWS Service Health Dashboard's own control plane depended on S3 US-EAST-1, so status could not be updated during the event.

Correction of errors (COE)

  • Modify the capacity-removal tool to remove capacity more slowly and to prevent it from taking any subsystem below its minimum required capacity level. AWS S3 · Committed (per official message)
  • Audit other operational tools for the same class of fast/unsafe capacity actions and add equivalent safety guards. AWS · Committed
  • Partition the S3 index subsystem into smaller cells so recovery is faster and blast radius is smaller; improve restart time of index/placement subsystems. AWS S3 · Committed
  • Change the AWS Service Health Dashboard to run across multiple regions so it can report status even when one region is impaired. AWS · Committed

Lessons learnt

  • Routine, well-practised operational commands are still high-consequence: guard destructive/scaling actions with rate limits and hard minimum-capacity floors, not just runbooks.
  • Subsystems that are never restarted accumulate hidden restart risk; exercise cold-start/recovery paths deliberately so real recovery time is known.
  • Single-region dependency concentration converts a component fault into a systemic one; understand and reduce cross-service blast radius.
  • Status/observability control planes must not depend on the very system whose health they report.

Improvements & remediation

  • Rate-limited capacity operations with enforced minimum-capacity guardrails on the S3 tooling.
  • Cellularization of the S3 index subsystem to shrink blast radius and speed recovery.
  • Multi-region AWS Service Health Dashboard so status reporting survives a regional impairment.
  • Broader operational-tool audit for unsafe fast-acting capacity actions.

Comprehensive analysis

Failure mechanism — why a capacity change became an outage

The command was a routine, authorized capacity-removal action, but the tooling had no floor on how much it could remove and no rate limit. Once removal crossed a threshold, the index and placement subsystems could not continue on the surviving fleet and had to cold-restart. The index subsystem is on the critical path of every S3 request — it resolves the physical location of each object — so its unavailability failed reads even though every byte of object data remained safely stored. The write path failed in parallel because the placement subsystem, which allocates new storage, both went down and itself depends on the index subsystem.

Why recovery took ~4.5 hours, not minutes

These subsystems had scaled to a very large footprint and had not been fully restarted for years. A cold start therefore had to load and integrity-check an enormous volume of metadata before it could safely serve traffic. The recovery time was dominated not by restarting processes but by the safety/consistency validation those processes must complete first — a latent, untested cost that only surfaced under a full restart. This is the classic 'we never exercise the recovery path, so we don't know its real duration' failure mode.

Blast radius — concentration risk

S3 US-EAST-1 is a foundational dependency: many other AWS services (EC2 launch, EBS, Lambda) and a large fraction of the public internet rely on it, often without the dependency being visible to the end operator. A fault in one storage subsystem in one region therefore propagated into a systemic, cross-service event. Critically, AWS's own Service Health Dashboard depended on S3 in the same region, so the primary status channel failed exactly when it was needed — an observability control plane must never share a failure domain with the system it observes.

Organizational / systemic factors

The proximate cause was human input error, but the incident is better read as a systems-design gap: safe, well-practised operations were allowed to take an irreversible, unbounded action with no guardrail, on subsystems whose recovery characteristics were unknown because they were never exercised. The durable fixes were structural (rate limits, minimum-capacity floors, cellularization, multi-region status) rather than 'be more careful' — the correct engineering response to human-error incidents.

Comparison & pattern

This sits in the same family as later large cloud events (e.g. the 2020 Kinesis thread-limit event and the 2025 DynamoDB DNS race, both also US-EAST-1 control-plane faults with wide cascades): a single-region control-plane component reaches an untested limit and takes down a shared dependency. The recurring lesson across all of them is blast-radius reduction (cells, regional isolation) and exercising recovery paths, not merely tightening runbooks.

Technical deep-dive

S3 in a region is composed of many subsystems; two are central here. The index subsystem holds the metadata and physical location of every object in the region and is consulted on every GET/LIST/HEAD request — if it is unavailable, reads fail even though the underlying data is intact. The placement subsystem allocates storage for new objects and is required for PUT; it also depends on the index subsystem. Removing a large tranche of capacity forced both into a full restart. Because these subsystems had scaled to a very large footprint and had not been restarted for years, the restart had to perform extensive integrity checks and metadata reconciliation before serving traffic, which dominated the ~4.5-hour recovery. The event is a canonical example of AWS's own Correction-of-Errors (COE) culture and Sequence-of-Events (SOE) postmortem discipline: a precise timeline, an honest single-sentence root cause (operator input error on a scaling command), and concrete, verifiable remediations (guardrails, cellularization, multi-region status).

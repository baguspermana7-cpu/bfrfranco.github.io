AWS Tokyo 2019: Cooling Control Failover Bug Overheats Part of a Zone

Amazon Web Services 2019-08-23 5h 54m to substantial restoration Coolingconfig-error
SummaryTimelineResponseFMEACausesActionsSources

Summary

On 23 August 2019 a bug in third-party cooling-control software hung the control system of an AWS Tokyo zone during a host failover. Air-handler PLCs hung too, so part of the hall lost cooling and even the manual purge failed. Servers overheated from 12:36 JST; cooling was back at 15:21 and most instances by 18:30.

Users affected
A small percentage of EC2 servers in one Tokyo zone and the services on them (RDS, Redshift, ElastiCache, WorkSpaces); Region-wide Auto Scaling launch errors for 90 minutes.

Root cause and contributing factors

TRIGGER: the datacenter control system that drives fans, chillers and air handlers in one Tokyo Availability Zone was failing away from one of its hosts. A bug in third-party control logic made the failover flood the field devices with interactions, and the control system stopped responding. COOLING CHAIN: the design says cooling goes to maximum when the control system fails. In most of the building it did.
Full root-cause narrative
In a small portion, PLCs on some air handling units had also become unresponsive, so the units shut down instead. The operators' manual fallback, purge mode, also ran through those PLCs and failed. Servers in the hot area powered off from 12:36 JST. RECOVERY: without the control system the team had little visibility. They reset equipment by hand, found and reset the air-handler PLCs, and cooling was back at 15:21. Most instances were back by 18:30; some on heat-damaged hardware were retired. LATENT ROOT: the fail-safe and the manual override both depended on the same PLCs, so the same software fault defeated the normal path, the safe default and the bypass.

Contributing factors by category

  • A bug in third-party control-system logic, triggered by a host failover, made the control system unresponsive (AWS summary).
  • PLCs on some air handling units also became unresponsive, so the units shut down instead of going to maximum cooling (AWS summary).
  • Purge mode, the manual bypass, still depended on those PLCs and failed (AWS summary).
  • With the control system down the operations team had minimum visibility of the cooling plant (AWS summary).
  • The idempotency-token path of RunInstances failed Region-wide, blocking Auto Scaling launches (AWS summary).
  • Heat and power loss damaged some hardware, so some instances and volumes had to be retired (AWS summary).

Analysis

Three layers, one weak point

Normal control, the fail-safe to maximum cooling, and the manual purge all ran through the same air-handler PLCs. When those hung, every layer failed in the affected area. Redundancy at the control-host level did not help, because the failover itself triggered the bug.

Blind operators

The control system was also the operators' window into the plant. Recovery meant walking the floor, checking and resetting equipment one by one, which took about two and three-quarter hours.

Small area, real damage

Only a small share of servers overheated, but some hardware was damaged and instances had to be retired. Heat is not always a clean shutdown.

API side effects

The idempotency-token path failed Region-wide for 90 minutes and blocked Auto Scaling, the tool customers would use to replace capacity.

What the summary does not say

It does not name the control-system vendor or the PLC model, the peak temperature, the number of affected servers, or when the purge bypass was finished.

Technical deep-dive
Building management systems are usually redundant at the server level, but a failover is itself a busy moment: the new host must re-learn the state of every device. Here that resync hit a bug and overwhelmed the devices. The cooling plant's fail-safe (go to maximum cooling on loss of supervisory control) is sound only if the local controllers still act on it. The PLCs on some air handlers had hung, so they neither kept running nor obeyed the purge command. AWS's lasting fix is to wire purge mode around the PLCs entirely, an approach it says its newest designs already use. The API symptoms were a separate path: launches using the idempotency token, which Auto Scaling relies on, failed across the Region for 90 minutes while ordinary launches in other zones worked.

Lessons learnt

  • A fail-safe and its manual override must not share the component most likely to fail with the primary path.
  • Control-system failover is a risky moment; test it against the real device population, not a lab.
  • Losing the building management system means losing visibility: keep independent temperature and airflow readings.
  • Operators need a drilled, fast reset procedure for controllers; AWS now expects to reset before customers notice.
  • Multi-zone designs held, but some load-balancer features still showed errors; test multi-zone behaviour under a zone fault.

Improvements

  • Controls: disable the failover mode that triggered the bug (AWS, done).
  • Controls: purge mode that bypasses the PLCs (AWS, in progress).
  • Operations: training for fast identification and reset (AWS, done).
  • Vendor: root cause of the third-party bug (AWS with vendors, in progress).
  • Analyst recommendation (not in the summary): independent temperature monitoring outside the BMS and periodic tests of the cooling fail-safe with the supervisor offline.

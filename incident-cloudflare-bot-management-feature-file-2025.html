Cloudflare Global Outage: Oversized Bot Management Feature File (November 18, 2025)

Cloudflare 2025-11-18 5h 46m core impact Software

On 18 November 2025 an 11:05 UTC ClickHouse database permissions change exposed r0-database table metadata alongside the default database. A Bot Management feature-file generator ran a metadata query over system.columns with no database filter, which then returned duplicated column rows and more than doubled the feature file's size past a hardcoded 200-feature preallocation limit (normal usage ~60 features). When the oversized file propagated network-wide, Cloudflare's FL2 proxy module panicked on a Rust unwrap of an Err value, causing core traffic to return 5xx errors. Customer impact began at 11:28 UTC; responders first suspected a DDoS/Workers KV problem before identifying the config file, deployed a correct file globally at 14:30 UTC, and fully restored all operations by 17:06 UTC.

Root cause

TRIGGER. At 11:05 UTC on 18 November 2025 Cloudflare deployed a permissions change to a ClickHouse database cluster to make previously-implicit access to underlying table metadata explicit: "Since users already have implicit access to underlying tables in r0, we made a change at 11:05 to make this access explicit." The change was rolled out gradually across the cluster, so at any moment some nodes had the new explicit grants and others did not. MECHANISM. A query that runs every five minutes generates the "feature" configuration file consumed by the Bot Management machine-learning model. That query enumerates column metadata from ClickHouse system tables but does not filter by database name. Before the change, implicit access meant it effectively returned a single logical set of columns. After explicit grants propagated, the same unfiltered query also matched metadata for underlying tables in the r0 database and "started returning 'duplicates' of columns because those were for underlying tables stored in the r0 database," so "the response now contained all the metadata of the r0 schema effectively more than doubling the rows in the response." SAFEGUARD THAT DID NOT HOLD. The Bot Management runtime preallocates memory against a fixed feature-count bound: "the Bot Management system has a limit on the number of machine learning features that can be used at runtime. Currently that limit is set to 200, well above our current use of ~60 features." The oversized, duplicate-laden file pushed the feature count past 200. Rather than being rejected gracefully, on the newer Rust-based FL2 proxy the loading code hit an Err result and called unwrap() on it, panicking the worker thread: "thread fl2_worker_thread panicked: called Result::unwrap() on an Err value." A panicked worker cannot serve the request, so FL2 returned HTTP 5xx. The size cap was a hard limit whose breach was not handled defensively at the point of consumption. BLAST RADIUS BY ENGINE VERSION. Impact differed by proxy generation but the legacy engine was NOT cleanly isolated: "Customers deployed on the new FL2 proxy engine, observed HTTP 5xx errors. Customers on our old proxy engine, known as FL, did not see errors, but bot scores were not generated correctly." FL therefore avoided 5xx but produced wrong/zero bot scores, which could cause customer bot rules to mis-fire. Migration status acted as an accidental partial boundary, not a designed failover. PROPAGATION. "The larger-than-expected feature file was then propagated to all the machines that make up our network." Because generation ran every five minutes and the permissions rollout was only partial, some cycles produced a good file and others a bad one: "every five minutes there was a chance of either a good or a bad set of configuration files being generated and rapidly propagated," so the system "would recover and then fail again," obscuring the cause. DETECTION AND RECOVERY. First errors were observed at 11:28 UTC; an automated test detected the issue at 11:31 and an incident call was created at 11:35. Diagnosis was hindered by the good/bad oscillation and by Cloudflare's own status page going down, which led "some of the team diagnosing the issue to believe that an attacker may be targeting both our systems as well as our status page." Cloudflare later stated: "The issue was not caused, directly or indirectly, by a cyber attack or malicious activity of any kind." A Workers KV and Cloudflare Access bypass was implemented at 13:05; rollback of the Bot Management file became the focus at 13:37; creation and propagation of new files was stopped at 14:24; a correct file was deployed globally at 14:30; and all services were resolved with impact ending at 17:06 UTC. Cloudflare called it "Cloudflare's worst outage since 2019."

Contributing factors

  • Unfiltered query lacking a database-name predicate: the feature-file generation query selected column metadata from ClickHouse system tables without filtering by database name, leaving it latently exposed to returning duplicate rows the moment the underlying r0 tables' metadata became visible.
  • Non-defensive consumption of a size-bounded input: the FL2 proxy relied on a hard 200-feature cap (against ~60 in use) but handled a breach with an unhandled Rust panic (unwrap() on an Err) rather than validating the file and degrading gracefully, converting a bad configuration input into customer-facing HTTP 5xx errors.
  • Partial/gradual permissions rollout across ClickHouse nodes: because explicit grants were applied progressively, some nodes produced good files and some bad ones, creating the every-five-minute good/bad oscillation that masked the cause and made the system appear to recover and then fail repeatedly.
  • Rapid automated propagation with no validation gate: the feature file was regenerated every five minutes and pushed network-wide automatically, so a single faulty query result was repeatedly distributed to all machines with no gate to halt propagation of an out-of-spec file.
  • Coincidental status-page outage and attack-like symptoms: Cloudflare's own status page went down during the incident, leading responders to suspect an external attacker targeting both their systems and the status page, which slowed accurate diagnosis.
  • Engine-version heterogeneity as the only partial boundary: FL2 customers saw 5xx while legacy FL customers instead received incorrect bot scores, so migration state limited but did not cleanly contain the blast radius, and there was no intentional failover or redundancy design.

Correction of errors (COE)

  • Harden ingestion of Cloudflare-generated configuration files, treating them as untrusted input in the same way user-generated input is validated. Not published · Committed (no owner/date/completion published)
  • Enable more global kill switches for features so a bad feature can be disabled network-wide quickly. Not published · Committed (no owner/date/completion published)
  • Eliminate the ability for core dumps or other error reports to overwhelm system resources during an incident. Not published · Committed (no owner/date/completion published)
  • Review failure modes for error conditions across all core proxy modules to remove hard-panic paths. Not published · Committed (no owner/date/completion published)

Lessons learnt

  • Internally generated configuration and data artifacts must be validated as strictly as external user input; trusting your own pipeline's output is a single point of failure.
  • Unqualified queries (here, a system.columns SELECT with no database filter) are a class of latent defect - they behave correctly until the surrounding schema/permissions context shifts, then silently return wrong results.
  • Fixed-size preallocation limits should fail gracefully (reject/degrade), never via a hard panic that crashes the request-serving path.
  • A permissions or access-control change in a data store can have far-reaching downstream effects on any pipeline that queries metadata; such changes need blast-radius review, not just local review.
  • Shared dependencies concentrate blast radius: routing Workers KV, Access and dashboard login through the same core proxy meant one module fault took down many services at once.
  • Fast automated detection (impact to detection in ~3 minutes) does not guarantee fast diagnosis - initial DDoS/Workers KV misattribution cost roughly two hours before the config file was identified.

Improvements & remediation

  • Add schema-aware validation and canary/health-gating on feature-file publish so an oversized or malformed file is caught before network-wide propagation.
  • Replace hard unwrap/panic paths in the FL2 proxy with bounded, fail-safe handling that drops or clamps oversized config rather than crashing the worker thread.
  • Explicitly qualify all metadata/config-generation queries with a database predicate and add tests that assert row-count stability against schema/permissions changes.
  • Introduce global per-feature kill switches so operators can disable a failing feature immediately without a full config rollback.
  • Decouple or add fallback paths for control-plane and critical services (dashboard login, Workers KV, Access) so they do not all fail together when one core-proxy module faults.
  • Add resource guards so core dumps and error reporting cannot exhaust node resources and deepen an incident.

Comprehensive analysis

Failure mechanism

The outage was a data-poisoning failure, not an infrastructure or capacity failure. A routine permissions change altered what a metadata query could see, and an unqualified SELECT over system.columns began returning duplicate column rows drawn from both the r0 and default databases. The Bot Management feature-file generator serialized those duplicated rows into a feature file that more than doubled in size. Every input on this path was individually valid - the query ran, the file was produced, propagation succeeded - yet the composed result violated a downstream invariant: a hardcoded 200-feature preallocation ceiling in the FL2 proxy against a normal load of about 60 features.

Why it cascaded

The proxy responded to the oversized file with a Rust panic - an unwrap on an Err value in the fl2_worker_thread - rather than rejecting or clamping the input. Because the FL2 core proxy sits on the request-serving path for a large fraction of Cloudflare-fronted traffic, that panic translated directly into 5xx errors globally. The blast radius widened because independent-seeming services shared this core path: Workers KV, Cloudflare Access, and dashboard login (through its Turnstile dependency) all degraded together, which both amplified user-visible impact and actively misled responders into chasing a Workers KV problem.

Detection, diagnosis and recovery

Automated testing flagged the problem within about three minutes of customer impact (11:28 -> 11:31 UTC) and an incident call opened at 11:35, so detection was fast. Diagnosis was not: symptoms resembled a DDoS and centered on Workers KV, and roughly two hours passed before attention shifted to the Bot Management config file at 13:37 UTC. Recovery then proceeded in stages - service bypasses at 13:05, halting propagation of new files at 14:24, deploying a correct file globally at 14:30 (main impact resolved), restoring the dashboard by scaling control-plane concurrency around 15:30, and full restoration at 17:06 UTC. The staged recovery shows the value of both a stop-the-bleeding step (halt propagation) and a fix-forward step (deploy good config).

Organizational and systemic factors

Three systemic patterns stand out. First, Cloudflare trusted its own generated configuration files on ingestion rather than validating them like user input - a control/data-plane boundary gap where internal artifacts bypass the scrutiny external ones receive. Second, a permissions change in one system (ClickHouse) propagated consequences into an unrelated pipeline (Bot Management), indicating change-review that did not account for cross-system metadata visibility. Third, the absence of an apparent canary or health-gate on feature-file publish meant there was no staged rollout to catch the bad file before it reached the whole network. Cloudflare's four committed remediations map directly onto these gaps, though none were published with owners, dates, or completion status.

Cross-incident pattern

This incident fits a recurring class of large-provider outages in which the trigger is a bad configuration or data push rather than hardware or attack, and the damage comes from a hard failure mode plus a shared dependency that concentrates blast radius. The distinctive lesson here is the unqualified-query defect: a query that is correct under one schema/permissions context silently produces poisoned output under another. Combined with fail-closed hard limits (a panic instead of graceful degradation) and network-wide propagation without canarying, a small, well-intentioned permissions change escalated into a multi-hour global outage affecting many of the world's most-used services.

Technical deep-dive

The failure chain is configuration-data corruption propagating into a code path that assumed well-formed input. Cloudflare's Bot Management uses a machine-learning model that ingests a "feature" configuration file, regenerated every five minutes by a query against a ClickHouse cluster. The query enumerates column metadata from ClickHouse system tables to assemble the feature list but does not filter by database name. Under the prior implicit-access model the query effectively returned one set of relevant columns. The 11:05 UTC change ("we made a change at 11:05 to make this access explicit") granted explicit access to underlying table metadata; ClickHouse then also surfaced metadata for the underlying tables in the r0 database. With no database-name predicate, the query "started returning 'duplicates' of columns because those were for underlying tables stored in the r0 database," so "the response now contained all the metadata of the r0 schema effectively more than doubling the rows in the response." The generated feature file therefore roughly doubled in row count. The runtime preallocates memory against a fixed feature bound: "the Bot Management system has a limit on the number of machine learning features that can be used at runtime. Currently that limit is set to 200, well above our current use of ~60 features." Doubling from ~60 pushed the count past 200. On FL2 — Cloudflare's newer Rust-based proxy engine — the code loading the feature file encountered the condition as an Err result and called Result::unwrap() on it, triggering a panic: "thread fl2_worker_thread panicked: called Result::unwrap() on an Err value." A panicked worker thread cannot serve the request, so FL2 returned HTTP 5xx. The legacy FL proxy did not emit 5xx but was not cleanly isolated: "Customers on our old proxy engine, known as FL, did not see errors, but bot scores were not generated correctly," meaning FL-served traffic received wrong/zero bot scores that could cause customer bot rules to mis-fire. Because the ClickHouse permissions rollout was gradual, only some nodes generated the oversized file at first; the five-minute regeneration cycle therefore alternated between valid and invalid files, each rapidly propagated network-wide, producing the recover-then-fail oscillation that obscured the cause and briefly led responders to suspect an attack (compounded by the coincidental failure of Cloudflare's own status page). Recovery required halting generation and propagation of new files (14:24 UTC), substituting a known-good earlier file and deploying a correct file globally (14:30 UTC), following an earlier Workers KV / Cloudflare Access bypass (13:05) and rollback focus (13:37); all services were resolved at 17:06 UTC. Cloudflare characterized the event as its "worst outage since 2019" and stated it "was not caused, directly or indirectly, by a cyber attack or malicious activity of any kind."

Google Cloud Accidentally Deletes UniSuper's Entire GCVE Private Cloud

Google Cloud (customer: UniSuper) 2024-05-02 216h 0m core impact Human errorSoftware

During the initial provisioning of UniSuper's Google Cloud VMware Engine (GCVE) Private Cloud, one input parameter was left blank in an internal Google deployment tool. Per Google's disclosure the blank value caused the system to assign a then-unknown default fixed one-year term to the Private Cloud, which silently armed an automatic-deletion action. Roughly a year later, at the end of that system-assigned term, the Private Cloud was deleted across both of its copies. The A$135B fund's 647,000+ members lost access to online services for nine days. The deletion did not reach data backups stored in Google Cloud Storage in the same region, which — together with third-party backup software — enabled a rebuild rather than permanent data loss. Members' account balances and investments were not lost, and the incident was operational, not a cyberattack.

Root cause

The incident originated in a latent provisioning fault created when UniSuper's Google Cloud VMware Engine (GCVE) Private Cloud was first stood up (in 2023, roughly a year before the deletion; Google did not publish the exact date). Google operators used an internal provisioning tool and left one input parameter blank. Per Google's official post-incident statement: \"One input parameter was left blank when using an internal tool to provision the customer's Private Cloud. As a result of the blank parameter, the system assigned a then unknown default fixed 1 year term value for this parameter.\" The blank field did not fail loudly or reject the request; the system silently substituted a default that configured the Private Cloud with a fixed one-year term whose expiry set the Private Cloud for deletion. This defaulting behaviour was, by Google's own account, \"then unknown\" to the operators — a hidden consequence of the tool's design rather than a deliberate choice. Google later confirmed it \"corrected the system behavior that sets GCVE Private Clouds for deletion for such deployment workflows.\"\n\nThe fault lay dormant for roughly a year. Nothing about the running environment appeared abnormal, so neither Google nor UniSuper had any signal that a deletion timer was counting down. On 2 May 2024, at the end of the system-assigned one-year term, the platform executed the scheduled action and deleted the customer's GCVE Private Cloud. Critically: \"No customer notification was sent because the deletion was triggered as a result of a parameter being left blank by Google operators using the internal tool, and not due a customer deletion request. Any customer-initiated deletion would have been preceded by a notification to the customer.\" Because the platform treated this as an internal lifecycle event rather than a customer-initiated destructive action, the guardrails that normally wrap customer deletions (advance notification, holds) were not on this path.\n\nThe customer's geographic redundancy did not defend against this failure mode. UniSuper had, per The Register, \"duplication in two geographies as a protection against outages and loss.\" But Google describes the deleted object as \"One of the customer's multiple GCVE Private Clouds (across two zones),\" and The Register reported that \"when the deletion of UniSuper's Private Cloud subscription occurred, it caused deletion across both of these geographies.\" Multi-zone redundancy defends against loss of a zone or region; it provided no defence when the parent Private Cloud spanning both zones was removed in a single operation — redundancy and failure occurred at different layers of the stack.\n\nWhat averted permanent data loss was backup outside the deleted Private Cloud. Google states: \"Data backups that were stored in Google Cloud Storage in the same region were not impacted by the deletion, and, along with third party backup software, were instrumental in aiding the rapid restoration.\" Those GCS objects survived because they were not part of the deleted GCVE Private Cloud's object graph, even though they sat in the same region. (Press reports additionally described backups held at another cloud provider; that specific claim is not in Google's official statement, which names only 'third party backup software,' and could not be independently verified here.)\n\nRecovery was manual and lengthy: Google and UniSuper teams \"worked 24x7 over several days to recover the customer's GCVE Private Cloud, restore the network and security configurations, restore its applications, and recover data to restore full operations\" — a rebuild-then-restore sequence, not a failover. Both companies publicly characterised the event as an \"isolated, 'one-of-a-kind occurrence' that has never before occurred with any of Google Cloud's clients globally.\" (Widely reported figures of ~500,000 affected members and an outage of about a week are not stated in Google's official statement and are not confirmed by the verified sources.)

Contributing factors

  • Unsafe default in the internal provisioning tool: leaving one input parameter blank did not fail the operation but silently substituted a then-unknown default that set a fixed one-year term after which the Private Cloud was set for deletion — converting an operator omission into a scheduled destructive action. Google later 'corrected the system behavior that sets GCVE Private Clouds for deletion for such deployment workflows.'
  • Manual, human-operated provisioning step: the Private Cloud was stood up via an internal tool operated by Google staff, exposing the workflow to input error. Google subsequently deprecated the tool, stating this 'is now fully automated and controlled by customers via the user interface, even when specific capacity management is required.'
  • Absence of notification on the deletion path: because the deletion was triggered by the blank-parameter term expiry rather than a customer request, 'No customer notification was sent' — unlike a customer-initiated deletion, which 'would have been preceded by a notification to the customer.'
  • Redundancy and failure at mismatched layers: UniSuper's protection was duplication across two geographies, but the deletion removed the parent GCVE Private Cloud spanning both zones, so per The Register 'it caused deletion across both of these geographies' — multi-geography redundancy gave no defence against removal of the container above the zones.
  • No proactive detection of the pending deletion: the one-year timer counted down invisibly for about a year, and neither official record describes any alerting; the failure surfaced only as a customer-facing outage on 2 May 2024.
  • Concentration of the live environment in a single provider's GCVE deployment, such that a single control-plane deletion took the service offline until a multi-day, 24x7 manual rebuild-and-restore.

Correction of errors (COE)

  • Eliminate the unsafe default: internal GCVE provisioning tooling must never silently substitute a destructive fixed-term/auto-deletion value for a blank input; require an explicit value or fail closed with no expiry. Google Cloud — GCVE provisioning/tooling engineering · Implied by postmortem
  • Add guardrails against subscription-level deletion of production Private Clouds: deletion cool-off / soft-delete window, mandatory second-person approval, and customer notification before any term-driven deletion executes. Google Cloud — GCVE platform/reliability · Recommended
  • Surface term/expiry state to operators and customers: make any fixed-term or scheduled-deletion attribute visible in tooling and customer consoles so an armed deletion timer cannot remain latent and unknown for a year. Google Cloud — GCVE product · Recommended
  • Preserve and validate independent, out-of-scope backups (GCS same-region + third-party backup software) and rehearse restore-from-backup for full Private Cloud reconstruction. UniSuper — infrastructure/DR; with Google Cloud · Validated in-incident (backups were instrumental to recovery)
  • Publish a transparent joint root-cause disclosure to reassure members that the event was operational, not a cyberattack or member-data compromise, and that balances were not lost. UniSuper + Google Cloud — communications/leadership · Done (joint statement 8 May; Google technical blog 25 May)

Lessons learnt

  • Defaults must fail safe. A blank field defaulting to an irreversible, delayed self-destruct is the antithesis of safe design; unsafe defaults on destructive actions are as dangerous as an explicit destructive command because no human ever consciously chose them.
  • Redundancy is not backup. Duplicate copies protect against regional failure, not against a valid control-plane instruction to delete the resource itself — such an instruction hits every copy at once. True recoverability came only from backups held outside the deletion's blast radius.
  • Latent misconfigurations with long fuses are uniquely dangerous. A destructive timer that stays invisible for a year defeats normal monitoring, change review, and incident-response reflexes because nothing appears wrong until the moment of loss.
  • Out-of-estate backups saved the fund. GCS same-region backups plus third-party backup software turned a potential permanent-data-loss catastrophe into a nine-day service outage — the single control that most changed the outcome.
  • Transparent, joint vendor-customer communication limited reputational damage: clearly stating this was an operational misconfiguration, not a cyberattack or member-data breach, and that member balances were not lost, was essential for a 647,000-member fund.
  • Even hyperscaler-managed platforms carry residual operational risk; customers of managed private clouds should assume misconfiguration is possible and retain independent, tested recovery paths they control.

Improvements & remediation

  • Fail-closed provisioning: internal tools reject or halt on missing parameters that control retention/lifecycle rather than substituting a destructive default.
  • Soft-delete and cool-off on Private Cloud deletion, with mandatory multi-party approval and advance customer notification before any term-driven or automated deletion.
  • Operator- and customer-visible display of any term, expiry, or scheduled-deletion attribute so armed timers cannot remain unknown.
  • Independent, out-of-scope backups (separate storage domain plus third-party backup software) as a standing requirement, with periodic full-reconstruction restore drills.
  • Proactive alerting on approaching lifecycle/retention deadlines so an impending automated deletion generates warnings well before execution.
  • Post-incident joint transparency reporting as standard practice for tenant-impacting control-plane errors.

Comprehensive analysis

Failure mechanism: a blank field became a one-year self-destruct

The proximate cause was mundane: while standing up UniSuper's GCVE Private Cloud through an internal deployment tool, a single input parameter was left blank. What made that omission catastrophic was the system's response — instead of rejecting the blank or defaulting to a benign no-expiry state, it substituted a then-unknown default fixed one-year term. That value quietly converted a permanent production resource into a time-limited one carrying an automatic-deletion action at term end. Google's own account is explicit that this was inadvertent misconfiguration, not a customer action, cyberattack, or hardware/data-integrity fault. The defect lives at the intersection of human factors and software design: whether a person left the field empty or the internal provisioning script passed a null value (Miles Ward's later account points to a script bug), the tooling amplified an ordinary omission into a destructive, irreversible outcome with a delayed fuse.

Why it hit both copies

UniSuper's Private Cloud was replicated across two copies — described as 'two geographies' in the joint statement and 'two zones' in Google's technical detail — an architecture intended to survive the loss of a single copy. It provided no defense here because the failure was not a regional outage; it was a valid, subscription-level deletion instruction generated by the platform's own lifecycle machinery. A control-plane 'delete this Private Cloud' action targets the logical resource, so both copies were removed together. This is the classic distinction between fault-tolerance and blast-radius containment: redundancy multiplies copies of the data but does not multiply protection against an authoritative command to destroy the resource. The single armed timer was, in effect, a correlated-failure source sitting above the redundancy layer, which is precisely why the outcome was total rather than degraded.

Recovery: backups outside the blast radius were the decisive control

The incident became a recoverable outage rather than a permanent loss for one reason: the deletion's scope did not include the data backups. Backups stored in Google Cloud Storage in the same region survived, and together with third-party backup software they were the instrumental basis for the rebuild. Customer and Google teams then worked 24x7 over several days to reconstruct the Private Cloud — re-establishing network and security configurations, restoring applications, and recovering data — before full operations returned. Member-facing online services were inaccessible for nine days and had to be rebuilt from those backups. The lesson is stark: the control that most changed the outcome was not the redundancy that failed, but the independent, out-of-estate backups that fell outside the deletion's reach.

Organizational and systemic factors

Several systemic weaknesses lined up. The internal tool embodied an unsafe default — a blank on a lifecycle-critical field mapped to a destructive terminal action instead of failing closed. The consequence was invisible: Google described the effect as 'then unknown', meaning no operator dashboard or customer console surfaced that a deletion timer had been armed, so the fault stayed latent for a full year, immune to normal change review and monitoring. And there was no independent circuit-breaker — no cool-off, second-person approval, or customer confirmation — between an expiring term and the irreversible destruction of an entire production estate. Any one of these controls, present, would likely have prevented the loss.

Cross-incident pattern: unsafe defaults and destructive automation

This event sits in a well-worn category of cloud and infrastructure failures where a routine operational input, mishandled by automation, produces disproportionate destruction. The recurring signature is: a human enters (or omits) a value, or a script passes a null; a system applies a permissive or destructive default without confirmation; the action executes at a scope that redundancy cannot contain; and recovery hinges on backups that happen to survive. The durable countermeasures are equally consistent across the pattern — fail-closed defaults on destructive fields, soft-delete/cool-off windows, multi-party approval for high-blast-radius actions, visible lifecycle state, and independent tested backups outside the primary estate. UniSuper's case is a textbook illustration that in large-scale infrastructure, the dangerous failures are often not dramatic attacks but quiet defaults with long fuses.

Technical deep-dive

The failure chain runs from a provisioning input to a scheduled lifecycle deletion. During initial deployment, an internal GCVE provisioning tool accepted a parameter governing the Private Cloud's term/lifecycle. When Google operators left it blank, the system did not reject the request; it applied a default. Per Google's statement, that default was a \"then unknown default fixed 1 year term value,\" and Google's remediation confirms the tool's logic could set \"GCVE Private Clouds for deletion for such deployment workflows.\" The Private Cloud therefore behaved normally at the data-plane level (VMs, networks, applications functioning) while carrying a hidden expiry disposition. (Google does not name the parameter or the tool, so the precise attribute is inferred from the stated behaviour.)\n\nThe destructive action was thus not a compute or storage fault but a scheduled lifecycle event: roughly a year later the term elapsed and the platform deleted the GCVE Private Cloud. Because the trigger was an internal term expiry rather than a customer request, the deletion took a path without the safeguards that wrap customer deletions: \"No customer notification was sent because the deletion was triggered as a result of a parameter being left blank... Any customer-initiated deletion would have been preceded by a notification to the customer.\"\n\nThe blast radius is explained by the object hierarchy. Google describes the deleted entity as \"One of the customer's multiple GCVE Private Clouds (across two zones),\" and The Register reported the deletion \"caused deletion across both of these geographies.\" UniSuper's redundancy — \"duplication in two geographies\" — was built at the zonal layer, below the parent Private Cloud that spanned both zones; removing that parent cascaded to both zonal deployments at once. (Note: Google's statement does not use the words 'subscription' or 'account'; The Register's 'Private Cloud subscription' phrasing is press wording layered on Google's 'Private Cloud across two zones.')\n\nRecoverability hinged on which artifacts were outside the deleted Private Cloud. Backups in Google Cloud Storage \"in the same region were not impacted by the deletion\" — same region, but a different service outside the GCVE Private Cloud's object graph — and, \"along with third party backup software, were instrumental in aiding the rapid restoration.\" (Some press accounts add backups at a second cloud provider; that is not in Google's official statement and is unverified here.) Recovery was a full rebuild-and-restore: re-provision the Private Cloud, reapply network and security configuration, redeploy applications, then reload data, with teams working \"24x7 over several days\" rather than an automatic failover. Google's remediation attacked the mechanism directly: it deprecated the internal tool (provisioning \"is now fully automated and controlled by customers via the user interface, even when specific capacity management is required\"), scrubbed the system database and manually reviewed all GCVE Private Clouds, and corrected the system behaviour that had set GCVE Private Clouds for deletion in such workflows — removing the unsafe default that turned a blank field into an expiry-and-delete.

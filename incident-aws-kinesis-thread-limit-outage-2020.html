AWS Kinesis OS Thread-Limit Cascade — US-EAST-1 (Nov 25, 2020)

Amazon Web Services 2020-11-25 17h 8m core impact Software

A small addition of capacity to the Kinesis Data Streams front-end fleet in US-EAST-1 pushed every server past an operating-system maximum thread-count limit. Because each front-end server creates OS threads for every other server in the fleet, the added hosts made the per-server thread count breach the OS ceiling; cache construction failed and servers were left with useless shard-maps, unable to route requests. Kinesis errored and slowed, and because many AWS services depend on Kinesis, CloudWatch, Cognito, Lambda, EventBridge and customer workloads cascaded down. Recovery was throttled by slow membership propagation and restart contention, so full Kinesis restoration took roughly 17 hours.

Root cause

The trigger was a small addition of capacity to the Kinesis Data Streams front-end fleet (begun 02:44 AM PST, finished 03:47 AM PST). Each front-end server creates OS threads for every other server in the fleet, so the per-server thread count scales with fleet size. The added capacity pushed every server past the maximum number of threads permitted by an operating-system configuration. As that limit was breached, shard-map cache construction failed to complete, leaving front-end servers with useless shard-maps and unable to route requests — producing fleet-wide errors and latency. AWS explicitly confirmed at 09:39 AM PST that the cause was the thread-limit breach and NOT memory pressure (the earlier leading hypothesis). AWS has not published the numeric OS thread ceiling or the pre-event per-host thread count, so the exact fleet size at which the limit trips cannot be computed from the disclosure.

Contributing factors

  • Thread-per-peer design: each front-end server holds OS threads for every other server, making per-server thread consumption O(fleet size) and turning a routine capacity add into a fleet-wide ceiling breach.
  • No fine-grained alarming on thread consumption, so the fleet crossed the OS thread limit without an early, specific warning; the first signal was downstream put/get errors ~1.5h later.
  • A monolithic (non-cellularized) front-end fleet meant thread growth was bounded by the whole fleet rather than a smaller cell, so the whole fleet was affected at once.
  • Slow cold-start and slow membership propagation (up to an hour to learn of new participants) plus restart contention capped recovery at a few hundred servers per hour, stretching restoration to ~12 hours after restart began.
  • Latent buffering bug in Cognito webservers: they could not survive sustained Kinesis API errors and exhausted their buffers, coupling Cognito authentication/credential availability to the Kinesis data plane.
  • CloudWatch buffered metric data with no local persistence limit, so during the outage buffering grew until it caused memory contention on downstream hosts — the mechanism that then propagated into Lambda invocation errors.
  • Operational blind spot: the primary Service Health Dashboard status tool depended on the impaired Cognito, and support engineers were not regularly trained on the backup status-communication tool.

Lessons learnt

  • Resource limits that scale with fleet size are latent scaling traps: a thread-per-peer model makes per-host thread usage grow with the whole fleet, so an ordinary, small capacity add can silently push every host over an OS ceiling at once.
  • Alarm on the failing resource, not just its symptoms: with no thread-consumption alarming, the first signal was downstream put/get errors ~1.5 hours after the breach — precious lead time lost to indirect detection.
  • Blast radius follows dependencies: a single data-plane service (Kinesis) coupled to CloudWatch, Cognito, Lambda and EventBridge turned one fleet's failure into a multi-service regional outage.
  • Design dependents to degrade, not die: latent buffering assumptions (Cognito exhausting buffers on upstream errors; CloudWatch metric buffers growing into memory contention that reached Lambda) converted a Kinesis fault into independent secondary failures.
  • Recovery must be planned as carefully as failure: slow membership propagation (up to 1h) and restart contention capped restart at a few hundred servers/hour, so the fix itself took ~12 hours — cold-start speed is a first-class reliability property.
  • Status-communication tooling must not share the failure domain it reports on: the primary dashboard depended on the impaired Cognito, so operators needed a rehearsed, independent backup channel.

Improvements & remediation

  • Bound the fault domain via cellularization of the front-end fleet so thread growth (and any similar resource pressure) is contained within a cell rather than the entire fleet.
  • Reduce per-host peer-thread pressure by consolidating onto larger CPU/memory servers and raising the tested OS thread-count limit, giving headroom against fleet-size-driven thread growth.
  • Add fine-grained thread-consumption alarming to detect the actual limiting resource before it manifests as downstream request errors.
  • Isolate high-fan-in tenants by moving large services like CloudWatch to a separate, partitioned front-end fleet and moving the front-end cache to a dedicated fleet.
  • Harden dependents against upstream failure: Cognito webservers now tolerate Kinesis errors without exhausting buffers, and CloudWatch persists 3 hours of metrics locally so alarms survive a Kinesis outage.
  • Make recovery faster and safer by radically improving cold-start time so a throttled, contention-limited restart no longer dominates the outage duration.
  • Decouple operational status communications from the services being reported on, and keep support engineers regularly trained on the independent backup tool.

Comprehensive analysis

Failure mechanism: a fleet-size-coupled resource limit

The front-end fleet used a design in which every server maintains OS threads for every other server in the fleet, so the per-server thread count is a function of fleet size. Adding even a small amount of capacity therefore raised the thread count on all existing hosts simultaneously. When that count crossed the operating-system's configured maximum thread ceiling, the servers could no longer complete construction of their shard-map cache. The result was not a clean crash but a corrupt operating state: front-end servers came up holding useless shard-maps and could not route requests, so the whole fleet degraded in unison rather than losing a subset of hosts.

Why it cascaded across AWS

Kinesis Data Streams sits beneath a wide set of AWS control- and data-plane services, so its degradation propagated by dependency. CloudWatch buffered metric data it could not flush, and that buffering grew until it caused memory contention on downstream hosts — which in turn raised AWS Lambda function-invocation error rates. Cognito User Pools suffered elevated API failures and latency because a latent buffering bug meant its webservers could not survive sustained Kinesis errors, exhausting buffers and blocking authentication and credential access. EventBridge / CloudWatch Events processing was delayed, which in turn slowed dependent Amazon ECS/EKS provisioning and scaling and AWS Auto Scaling policies. One fleet's internal limit thus became a regional, multi-service event.

Recovery: why it took ~17 hours

Restoration could not be rushed. AWS first had to carefully reduce thread counts and remove the added capacity, then bring servers back gradually. Two properties throttled this: it takes up to an hour for any existing fleet member to learn of new participants, and restarting too quickly creates contention between membership propagation and handling incoming requests, starving request-handling and re-inducing errors. Consequently AWS could only add servers at a few hundred per hour. Restart began at 10:07 AM PST but Kinesis did not fully normalize until 10:23 PM PST — roughly 12 hours later. Dependent services recovered on their own tracks: Cognito normal by 2:18 PM, EventBridge largely resolved by 4:15 PM, CloudWatch fully recovered by 10:31 PM PST.

Organizational and systemic factors

Several systemic gaps amplified the event. There was no fine-grained alarm on thread consumption, so the first indication was indirect (put/get errors) about 1.5 hours after the breach. The front-end fleet had not yet been cellularized the way the back-end had, so there was no bulkhead to contain the thread growth to a subset. Downstream services embedded fragile assumptions (Cognito buffer exhaustion; CloudWatch unbounded metric buffering) that turned an upstream fault into independent secondary failures. And operational communication was itself in the blast radius: the primary Service Health Dashboard depended on the impaired Cognito, and support engineers were not routinely trained on the backup tool.

Cross-incident pattern

This event exemplifies a recurring class of large-scale outages: a routine, low-risk operational change (a small capacity add) interacts with a resource limit that scales with system size, and the fault then propagates along a hidden dependency web from a foundational service outward. The remediations — cellularization to bound fault domains, alarming on the true limiting resource, hardening dependents to degrade rather than fail, isolating high-fan-in tenants, and decoupling status tooling from the services it monitors — are the same structural defenses that recur across major cloud incidents. Notably, no dollar cost or affected-user count was published for this specific event, and the widely cited ~$34M Parametrix figure pertains to the separate December 7, 2021 US-EAST-1 outage, not this one.

Technical deep-dive

The front-end tier of Kinesis Data Streams routes producer/consumer requests to the correct back-end shards using an in-memory shard-map, and it discovers and tracks its peers by maintaining an OS thread per peer server. That thread-per-peer construction makes the resident thread count on any single host proportional to the size of the entire front-end fleet — an O(N) coupling that is invisible under steady state but becomes the dominant scaling term whenever the fleet grows. On November 25, 2020, a small capacity addition (02:44–03:47 AM PST) increased N enough that the per-host thread total crossed a maximum-thread ceiling imposed by an operating-system configuration. Critically, the failure surfaced during cache (shard-map) construction: as the thread ceiling was hit, cache build could not complete, and servers finished startup holding useless shard-maps. With no valid shard-map, a front-end server cannot map an incoming request to a back-end shard, so requests error out — a correctness failure of the routing layer, not mere overload. AWS investigated memory pressure as the leading hypothesis and explicitly disconfirmed it at 09:39 AM PST, isolating the OS thread limit as the true cause. Remediation had to respect two operational realities of the peer-membership subsystem: membership convergence is slow (up to an hour for an existing member to learn of a new participant), and the CPU/memory a server spends converging membership contends with the resources it needs to serve traffic. Bringing hosts back too fast therefore re-manifested the outage as elevated errors and latency, so AWS was forced to a few-hundred-servers-per-hour restart cadence after first reducing thread counts and removing the added capacity. AWS did not disclose the numeric thread ceiling, the pre-event per-host thread count, the peer-messaging concurrency model (e.g., whether thread-per-peer is a blocking-IO worker model versus a framework artifact, and why async multiplexing was not used), or the membership protocol (gossip versus central push) behind the one-hour convergence figure — so the exact N at which the limit trips and the precise convergence mechanics remain qualitative in the public record.

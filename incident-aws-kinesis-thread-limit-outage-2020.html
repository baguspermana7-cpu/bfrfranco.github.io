AWS Kinesis OS Thread-Limit Cascade — US-EAST-1 (Nov 25, 2020)

Amazon Web Services 2020-11-25 17h 8m core impact Software

A small addition of capacity to the Kinesis Data Streams front-end fleet in US-EAST-1 pushed every server past an operating-system maximum thread-count limit. Because each front-end server creates OS threads for every other server in the fleet, the added hosts made the per-server thread count breach the OS ceiling; cache construction failed and servers were left with useless shard-maps, unable to route requests. Kinesis errored and slowed, and because many AWS services depend on Kinesis, CloudWatch, Cognito, Lambda, EventBridge and customer workloads cascaded down. Recovery was throttled by slow membership propagation and restart contention, so full Kinesis restoration took roughly 17 hours.

Root cause

The trigger — explicitly labeled by AWS as the trigger and NOT the root cause — was a small capacity addition to the Amazon Kinesis Data Streams front-end fleet in US-EAST-1, which 'began to be added to the service at 2:44 AM PST, finishing at 3:47 AM PST.' The front-end's role is narrow but foundational: 'It handles authentication, throttling, and request-routing to the correct stream-shards on the back-end clusters.' The actual root cause was an architectural coupling in the front-end's peer-coordination design: 'each front-end server creates operating system threads for each of the other servers in the front-end fleet,' so 'the total threads each server must maintain is directly proportional to the number of servers in the fleet' — thread consumption scales with fleet size N, not with traffic. Adding servers therefore raised the per-server thread count on every existing server as well as the new ones. Once the enlarged fleet was fully in service, 'the new capacity had caused all of the servers in the fleet to exceed the maximum number of threads allowed by an operating system configuration.' Crossing that OS-configured per-process ceiling did not cleanly crash the servers; it broke their routing state: 'As this limit was being exceeded, cache construction was failing to complete and front-end servers were ending up with useless shard-maps that left them unable to route requests to back-end clusters.' Because every server crossed the same shared limit at nearly the same time, and because the front-end (unlike the already-cellularized back-end) was not yet cellularized, the failure hit the whole fleet at once. First alarms fired at 5:15 AM PST; AWS narrowed the cause and determined a full front-end restart was required at 7:51 AM PST, confirmed root cause at 9:39 AM PST, took first traffic on recovered servers at 10:07 AM PST, and fully restored Kinesis at 10:23 PM PST. Recovery was slow because the same coordination design throttled it: 'It takes up to an hour for any existing front-end fleet member to learn of new participants,' and 'bringing front-end servers back online too quickly would create contention... [so] we could only add servers at the rate of a few hundred per hour.' Numerous AWS services that depend on Kinesis for telemetry and eventing — Cognito, CloudWatch, Lambda, and ECS/EKS (via EventBridge) — were degraded as a downstream cascade.

Contributing factors

  • Architectural coupling of thread count to fleet size: each front-end server spawns one OS thread per other server in the fleet ('each front-end server creates operating system threads for each of the other servers in the front-end fleet'), so per-server thread consumption grows O(N) with fleet size rather than with load. Scaling the fleet up — normally a capacity/safety action — was itself the destabilizing force that pushed every server past the OS thread limit.
  • A hard OS-level maximum-threads-per-process configuration with insufficient headroom: 'the new capacity had caused all of the servers in the fleet to exceed the maximum number of threads allowed by an operating system configuration.' A modest capacity addition was enough to exceed it fleet-wide, and AWS's remediation to 'finish testing an increase in thread count limits' indicates the limit had not been raised ahead of fleet growth.
  • Absence of cellularization on the front-end fleet (unlike the back-end, which AWS had already cellularized — 'accelerate the cellularization of the front-end fleet to match what we've done with the back-end'): there was no bulkhead to isolate the failure, so every front-end server hit the same shared OS limit simultaneously and failed together, giving the fault region-wide front-end blast radius.
  • Fragile recovery dynamics baked into the same coordination design: 'It takes up to an hour for any existing front-end fleet member to learn of new participants,' and 'bringing front-end servers back online too quickly would create contention... [so] we could only add servers at the rate of a few hundred per hour,' turning restoration into a multi-hour process (first traffic 10:07 AM PST, full recovery 10:23 PM PST).
  • Wide blast radius via service dependencies on Kinesis for telemetry and eventing — 'Amazon Cognito uses Kinesis Data Streams to collect and analyze API access patterns,' 'CloudWatch uses Kinesis Data Streams for the processing of metric and log data,' 'Lambda function invocations currently require publishing metric data to CloudWatch as part of invocation,' and 'Elastic Container Service (ECS) and Elastic Kubernetes Service (EKS) both make use of EventBridge to drive internal workflows' — so a single-fleet fault cascaded into broad multi-service impairment.
  • Delayed diagnosis: first alarms at 5:15 AM PST, but the team did not narrow to a couple of candidate causes and determine that a full front-end restart was required until 7:51 AM PST, and did not confirm root cause until 9:39 AM PST, extending time-to-mitigate.

Correction of errors (COE)

Lessons learnt

  • Resource limits that scale with fleet size are latent scaling traps: a thread-per-peer model makes per-host thread usage grow with the whole fleet, so an ordinary, small capacity add can silently push every host over an OS ceiling at once.
  • Alarm on the failing resource, not just its symptoms: with no thread-consumption alarming, the first signal was downstream put/get errors ~1.5 hours after the breach — precious lead time lost to indirect detection.
  • Blast radius follows dependencies: a single data-plane service (Kinesis) coupled to CloudWatch, Cognito, Lambda and EventBridge turned one fleet's failure into a multi-service regional outage.
  • Design dependents to degrade, not die: latent buffering assumptions (Cognito exhausting buffers on upstream errors; CloudWatch metric buffers growing into memory contention that reached Lambda) converted a Kinesis fault into independent secondary failures.
  • Recovery must be planned as carefully as failure: slow membership propagation (up to 1h) and restart contention capped restart at a few hundred servers/hour, so the fix itself took ~12 hours — cold-start speed is a first-class reliability property.
  • Status-communication tooling must not share the failure domain it reports on: the primary dashboard depended on the impaired Cognito, so operators needed a rehearsed, independent backup channel.

Improvements & remediation

  • Bound the fault domain via cellularization of the front-end fleet so thread growth (and any similar resource pressure) is contained within a cell rather than the entire fleet.
  • Reduce per-host peer-thread pressure by consolidating onto larger CPU/memory servers and raising the tested OS thread-count limit, giving headroom against fleet-size-driven thread growth.
  • Add fine-grained thread-consumption alarming to detect the actual limiting resource before it manifests as downstream request errors.
  • Isolate high-fan-in tenants by moving large services like CloudWatch to a separate, partitioned front-end fleet and moving the front-end cache to a dedicated fleet.
  • Harden dependents against upstream failure: Cognito webservers now tolerate Kinesis errors without exhausting buffers, and CloudWatch persists 3 hours of metrics locally so alarms survive a Kinesis outage.
  • Make recovery faster and safer by radically improving cold-start time so a throttled, contention-limited restart no longer dominates the outage duration.
  • Decouple operational status communications from the services being reported on, and keep support engineers regularly trained on the independent backup tool.

Comprehensive analysis

Failure mechanism: a fleet-size-coupled resource limit

The front-end fleet used a design in which every server maintains OS threads for every other server in the fleet, so the per-server thread count is a function of fleet size. Adding even a small amount of capacity therefore raised the thread count on all existing hosts simultaneously. When that count crossed the operating-system's configured maximum thread ceiling, the servers could no longer complete construction of their shard-map cache. The result was not a clean crash but a corrupt operating state: front-end servers came up holding useless shard-maps and could not route requests, so the whole fleet degraded in unison rather than losing a subset of hosts.

Why it cascaded across AWS

Kinesis Data Streams sits beneath a wide set of AWS control- and data-plane services, so its degradation propagated by dependency. CloudWatch buffered metric data it could not flush, and that buffering grew until it caused memory contention on downstream hosts — which in turn raised AWS Lambda function-invocation error rates. Cognito User Pools suffered elevated API failures and latency because a latent buffering bug meant its webservers could not survive sustained Kinesis errors, exhausting buffers and blocking authentication and credential access. EventBridge / CloudWatch Events processing was delayed, which in turn slowed dependent Amazon ECS/EKS provisioning and scaling and AWS Auto Scaling policies. One fleet's internal limit thus became a regional, multi-service event.

Recovery: why it took ~17 hours

Restoration could not be rushed. AWS first had to carefully reduce thread counts and remove the added capacity, then bring servers back gradually. Two properties throttled this: it takes up to an hour for any existing fleet member to learn of new participants, and restarting too quickly creates contention between membership propagation and handling incoming requests, starving request-handling and re-inducing errors. Consequently AWS could only add servers at a few hundred per hour. Restart began at 10:07 AM PST but Kinesis did not fully normalize until 10:23 PM PST — roughly 12 hours later. Dependent services recovered on their own tracks: Cognito normal by 2:18 PM, EventBridge largely resolved by 4:15 PM, CloudWatch fully recovered by 10:31 PM PST.

Organizational and systemic factors

Several systemic gaps amplified the event. There was no fine-grained alarm on thread consumption, so the first indication was indirect (put/get errors) about 1.5 hours after the breach. The front-end fleet had not yet been cellularized the way the back-end had, so there was no bulkhead to contain the thread growth to a subset. Downstream services embedded fragile assumptions (Cognito buffer exhaustion; CloudWatch unbounded metric buffering) that turned an upstream fault into independent secondary failures. And operational communication was itself in the blast radius: the primary Service Health Dashboard depended on the impaired Cognito, and support engineers were not routinely trained on the backup tool.

Cross-incident pattern

This event exemplifies a recurring class of large-scale outages: a routine, low-risk operational change (a small capacity add) interacts with a resource limit that scales with system size, and the fault then propagates along a hidden dependency web from a foundational service outward. The remediations — cellularization to bound fault domains, alarming on the true limiting resource, hardening dependents to degrade rather than fail, isolating high-fan-in tenants, and decoupling status tooling from the services it monitors — are the same structural defenses that recur across major cloud incidents. Notably, no dollar cost or affected-user count was published for this specific event, and the widely cited ~$34M Parametrix figure pertains to the separate December 7, 2021 US-EAST-1 outage, not this one.

Technical deep-dive

The Kinesis Data Streams front-end is a thin routing/authentication tier: 'It handles authentication, throttling, and request-routing to the correct stream-shards on the back-end clusters.' To route requests it maintains a shard-map cache. Critically, front-end servers must stay coordinated about fleet membership, and the implementation does this per-peer: 'each front-end server creates operating system threads for each of the other servers in the front-end fleet.' This makes per-server thread usage O(N) in fleet size N — 'the total threads each server must maintain is directly proportional to the number of servers in the fleet' — and independent of request volume. As long as N stayed low enough that O(N) coordination threads (plus the server's other threads) fit under the OS-configured per-process ceiling, the fleet was stable. The November 25 capacity addition (2:44 AM to 3:47 AM PST), which AWS calls the 'trigger, though not root cause,' increased N. Because the thread cost is borne by every server, not just the new ones, the addition raised thread counts fleet-wide at once, and 'the new capacity had caused all of the servers in the fleet to exceed the maximum number of threads allowed by an operating system configuration.' The failure mode was not a clean crash: when a server could not create the threads it needed, its shard-map build did not finish — 'cache construction was failing to complete and front-end servers were ending up with useless shard-maps that left them unable to route requests to back-end clusters.' Because every server crossed the threshold at nearly the same time, the fleet degraded coherently rather than partially, which is why customer errors were broad once alarms fired at 5:15 AM PST. Recovery was constrained by the same coordination design that caused the fault: 'It takes up to an hour for any existing front-end fleet member to learn of new participants,' and 'bringing front-end servers back online too quickly would create contention between these two needs and result in very few resources being available to handle incoming requests,' so servers could be re-added only 'at the rate of a few hundred per hour.' This is why, despite root-cause confirmation at 9:39 AM PST and first servers taking traffic at 10:07 AM PST, full restoration took until 10:23 PM PST. AWS's stated remediations attack the mechanism from three angles: 'moving to larger CPU and memory servers, reducing the total number of servers and, hence, threads required by each server to communicate across the fleet' (smaller N); 'finish testing an increase in thread count limits in our operating system configuration' (more headroom under the ceiling); and 'accelerate the cellularization of the front-end fleet to match what we've done with the back-end' (bounding N per cell and containing blast radius).

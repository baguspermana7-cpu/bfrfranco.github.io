Google Cloud Global Service Control / IAM Outage — June 12, 2025

Google Cloud 2025-06-12 7h 27m core impact Software

A latent, unguarded code path in Google Cloud's Service Control quota system — added on 2025-05-29 without error handling or feature-flag protection — was triggered on 2025-06-12 when a policy change containing unintended blank fields was inserted into the regional Spanner tables Service Control reads for policy data. The blank metadata replicated globally within seconds; regional quota checks pulled the blank fields, exercised the unprotected path, dereferenced a null pointer, and, with no error handling to contain it, the Service Control binaries crashed and entered a global crash loop. Because Service Control gates API authorization, IAM could no longer issue tokens and most Google Cloud APIs failed worldwide for several hours. The failure cascaded into downstream platforms that depend on GCP, most notably Cloudflare, whose Workers KV backend relied on the affected infrastructure.

Root cause

A latent, unguarded code path was introduced into Service Control on 2025-05-29 to perform additional quota policy checks; it had neither error handling nor feature-flag protection. On 2025-06-12 at ~10:45 PDT a policy change carrying unintended blank fields was inserted into the regional Spanner policy tables Service Control reads, and this metadata replicated globally within seconds. Regional quota checks pulled the blank fields, exercised the unprotected path, dereferenced a null pointer, and — with no error handling to contain the fault — the Service Control binaries crashed and entered a synchronized global crash loop. Because Service Control authorizes API requests, IAM could no longer issue tokens and most Google Cloud APIs failed worldwide.

Contributing factors

  • Code change lacked error handling on a critical binary code path, so a null dereference crashed the binary rather than degrading gracefully.
  • Change was not feature-flag protected, so it activated globally at once with no incremental exposure or blast-radius containment (Google notes flag protection would have caught the issue in staging).
  • Service Control read globally-replicated policy metadata that was not validated for blank/malformed fields before use.
  • Global replication of policy metadata within seconds meant a single bad insert propagated to every region almost instantly, giving no time-to-detect buffer.
  • Recovery was constrained by a herd effect: restarting Service Control tasks en masse threatened to overload the underlying infrastructure. Missing randomized exponential backoff plus the need to throttle task creation and route to multi-regional databases lengthened resolution in the largest region (us-central1).
  • Deep, shared dependency on Service Control / IAM as a single global control-plane chokepoint meant one component's failure took down ~70+ products and cascaded to external platforms.

Correction of errors (COE)

  • Modularize Service Control so it fails open — serving degraded results rather than crashing — when it encounters invalid or blank metadata. Google Cloud — Service Control · committed
  • Enforce that all changes to critical binaries are feature-flag protected and rolled out incrementally rather than activated globally and instantly. Google Cloud · committed
  • Improve static analysis and testing practices to catch this class of defect (unhandled null/exception on a critical path) before it ships. Google Cloud · committed
  • Audit all systems that consume globally-replicated data for equivalent unvalidated-input exposure, and ensure such data is propagated/consumed safely. Google Cloud · committed
  • Audit and ensure Service Control uses randomized exponential backoff on task restart/retry to prevent the herd effect that overloaded infrastructure during recovery. Google Cloud — Service Control · committed
  • Ensure monitoring and external customer-communication infrastructure remains operational even when Google Cloud itself is down, so customers get information as soon as possible. Google Cloud · committed

Lessons learnt

  • Critical control-plane code must fail open, not crash — a null dereference on invalid input should degrade service, never take down a global authorization path.
  • Every change to a globally-replicated, blast-radius-wide system must ship behind a feature flag with incremental rollout; instant global activation removes the only chance to catch a bad change in staging before it is everywhere.
  • Systems that consume globally-replicated metadata must validate that data at the point of use; a single blank-field insert replicating in seconds is enough to weaponize an unvalidated read path across every region.
  • Recovery of a large control plane is itself a distributed-systems problem — mass task restarts create a herd effect, so recovery needs randomized exponential backoff, throttled task creation, and load re-routing, which realistically lengthens time-to-restore in the biggest regions.
  • Concentrating authorization in one shared component (Service Control/IAM) makes it a single point of failure whose blast radius spans ~70+ products and cascades to external customers who depend on GCP.
  • Monitoring and customer-communication tooling must not share fate with the platform they observe; when Google Cloud went down, the ability to monitor and communicate must survive independently.

Improvements & remediation

  • Introduce fail-open modularization in Service Control so invalid metadata yields degraded-but-available authorization instead of a crash loop.
  • Mandate feature-flagged, incremental rollout for all changes to global control-plane systems, replacing instant global activation.
  • Add error handling and static-analysis/testing coverage across critical binary code paths to catch unhandled null/exception conditions pre-release.
  • Systematically audit and harden all consumers of globally-replicated data against blank/malformed inputs.
  • Stand up monitoring and external-communication infrastructure that remains operational independently of Google Cloud's own health.
  • Adopt throttled, load-aware recovery procedures — randomized exponential backoff, task-creation throttling, and multi-regional database routing — as a standard playbook to avoid herd-effect overload during control-plane restarts.

Comprehensive analysis

Failure mechanism

The outage was a textbook latent-defect-meets-bad-data failure. On 2025-05-29 a quota-policy-check feature entered Service Control without error handling or a feature flag, creating a dormant, unguarded code path. It stayed inert until 2025-06-12, when a policy insert with unintended blank fields landed in the regional Spanner policy tables. When quota checks read those blank fields, they exercised the unguarded path and dereferenced a null pointer. With nothing to catch the fault, the binaries did not degrade — they crashed, and immediately restarted into the same poisoned state, producing a self-sustaining crash loop.

Why it cascaded

Two amplifiers turned a local defect into a global outage. First, the triggering metadata replicated to every region within seconds, so there was no staggered exposure and effectively no detect-and-halt window — every region hit the null pointer at nearly the same moment. Second, Service Control sits on the authorization critical path: when it crash-looped, IAM could not issue tokens, and without tokens most Google Cloud APIs across ~70+ products failed simultaneously. The blast radius then extended beyond Google: platforms built on GCP failed downstream, most notably Cloudflare, whose Workers KV backend depended on the affected infrastructure, dragging down Durable Objects/D1, AI Gateway, Pages, Stream, Realtime and Images for roughly a 2.5-hour window (17:52–20:28 UTC; Cloudflare states the outage lasted 2h28m).

Detection, mitigation and recovery

Mitigation was fast; full recovery was deliberately slow. Engineers identified the offending path and completed a 'red-button' rollout within ~40 minutes of the 10:51 PDT begin, after which regions recovered smaller-first. But bringing Service Control back was itself a distributed-systems hazard: restarting all tasks at once risked a herd-effect overload of the underlying infrastructure. Google therefore throttled Service Control task creation and routed traffic to multi-regional databases to shed load, which is why us-central1 — the largest region — took up to ~2h40m to fully resolve (implying ~13:31 PDT, an arithmetic estimate). The incident was declared over at 18:18 PDT, ~7h27m end-to-end, with status-page posts continuing to 23:34 PDT (12 Jun) and 16:45 PDT (13 Jun) as post-incident publication rather than new impact.

Organizational and systemic factors

The corrective actions read as an admission that process guardrails, not just code, failed. A change reached a global, blast-radius-wide system with neither error handling nor a feature flag, and a consumer of globally-replicated data trusted that data without validating it. The remediation set — fail-open modularization, mandatory incremental feature-flagged rollout, static analysis on critical paths, an audit of all global-metadata consumers, randomized exponential backoff to blunt the recovery herd effect, and independent monitoring/communication infrastructure — targets each systemic gap. The last item is notable: it concedes that observability and customer comms shared fate with the platform, so operators were partly blind and constrained in communicating precisely when they most needed both.

Cross-incident pattern

This incident fits a recurring cloud-era failure archetype: a single shared control-plane component (identity/authorization/quota) becomes a global single point of failure, and a benign-looking configuration or metadata change — not a hardware fault — triggers correlated, simultaneous failure everywhere at once. The same shape recurs across major providers: unvalidated input or a bad config replicates faster than humans can react, an unhandled exception converts a data problem into a crash, and deep dependency graphs turn one vendor's control-plane outage into a multi-company internet event. The durable lesson across all of them is identical to Google's own action items: validate replicated inputs, fail open on the critical path, and roll changes out incrementally with flags.

Technical deep-dive

Service Control is Google Cloud's per-request policy/quota enforcement layer that gates API authorization; IAM token issuance and virtually all Google Cloud API traffic transit it. On 2025-05-29 a feature adding additional quota policy checks was merged with two defects that only mattered together: no error handling around the new logic, and no feature flag to gate its activation. The path was reachable but never exercised on a value that would fault it — until 2025-06-12 ~10:45 PDT, when a policy change with unintended blank fields was written to the regional Spanner tables that Service Control consults for policy data. Spanner's global replication propagated that record to every region within seconds, so the poisoned metadata was ubiquitous before any human or automated guard could quarantine it. At the next quota evaluation in each region, Service Control read the blank fields, entered the unguarded May-29 branch, and performed a null-pointer dereference. Absent a try/catch or equivalent boundary, the null did not surface as a handled error or a degraded (fail-open) response — it crashed the binary. Crucially, the crash was deterministic and input-driven: on restart the task re-read the same replicated policy state, re-hit the same null, and crashed again, producing a synchronized global crash loop rather than an isolated flap. Because the loop disabled the authorization plane, IAM could not mint tokens and dependent APIs across ~70+ products returned errors worldwide. The engineered mitigation was a 'red-button' disable of the offending path, completed within ~40 minutes, but recovery exposed a second-order distributed-systems constraint: simultaneously restarting a very large fleet of Service Control tasks would create a herd effect against the underlying infrastructure and the policy/database tier it depends on. Google therefore throttled task creation and routed load to multi-regional databases, trading a slower restore (up to ~2h40m in us-central1) for controlled recovery instead of a secondary overload. The remediation directly maps to the failure primitives: fail-open modularization (a null/invalid-metadata condition must yield degraded service, not a crash), feature-flagged incremental rollout (bound the blast radius of any new path), input validation on consumers of globally-replicated data (blank fields must never reach a live code path), static analysis and testing to catch unhandled dereferences before release, randomized exponential backoff on restart to avoid herd-effect recovery overload, and fate-independent monitoring/comms (so the control plane's failure does not blind its own operators).

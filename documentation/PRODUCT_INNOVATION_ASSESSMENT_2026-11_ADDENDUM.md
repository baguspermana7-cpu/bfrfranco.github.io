### Q6. Simulation honesty layer (priority 74.5)
- **Current limitation:** Simulated or static figures sit beside ticking clocks and "Live" titles: the PLN page, datahallAI "Gateways 16/16", random datahall alarms. Four cockpits (fuel-system, EPMS, dc-conventional, cdu-mini-bms) have no simulated-data banner. The LTC lab (`ltc-system-modelling-lab.js:2704`) and DCMOC fall back to local constants silently.
- **Transformation:** Every figure that is not measured telemetry says what it is (simulated, snapshot with an as-of date, or model fallback), from one shared component that a gate enforces.
- **User experience:** A small mono line under each panel title, for example "SIMULATED · scenario CRAH-trip" or "SNAPSHOT · PLN AR 2024 · data 2026-04-29". When a model falls back, the panel shows "fallback model: constants v…" instead of passing silently.
- **Workflow:** The page loads, `RZProvenance.mark(el, {kind, source, asOf})` renders the line, and the gate reads every `[data-rz-provenance]` node.
- **Value:** It protects the ACCURACY rule in CLAUDE.md and the site's credibility with engineers, who distrust a "Live" label they can disprove.
- **Technical implementation:**
  - A ~60-line `js/rz-provenance.js`.
  - The attribute is added on the PLN, datahall, datahallAI, fuel, EPMS, dc-conventional and cdu-mini-bms pages.
  - Fallback paths call `mark(..., {kind: 'fallback'})`.
- **Integration points:** cockpit pages, `js/pln-*-data.js` headers (version and date are already present), the LTC lab, DCMOC.
- **Complexity:** Low
- **Effort:** 1.5 weeks (score 2)
- **Impact:** 7/10
- **Innovation:** 4/10
- **Confidence:** 9/10
- **Dependencies and risks:** The copy must stay plain. Risk: the label reads as noise if it is styled as a badge. Use the existing mono basis-line idiom.
- **Acceptance criteria:**
  - Gate: on each listed page, every KPI panel has a provenance line, and no element contains "Live" unless its kind is `telemetry`.
  - Red on today's tree (PLN fails).
  - Forcing a fallback in the LTC lab shows the line.

### Q7. Scripted fault scenarios in the data-hall cockpits (priority 73.0)
- **Current limitation:** `datahall.html` picks a random zone and CRAH every 120 s. The alarm has no cause, no consequence and no expected response, and it breaks ACCURACY.
- **Transformation:** A library of deterministic scenarios replaces chance. Each scenario has a timeline of plant states driven by the engine, an alarm sequence, and the expected operator actions.
- **User experience:**
  - The user picks "Scenario: CRAH-3 fan failure at 70 % load", then presses play, pauses and steps through it.
  - Temperatures rise at rates from the engine's thermal model.
  - After each alarm, a side panel shows "expected action" and "time budget".
  - At the end, a debrief compares the user's acknowledgements and timings with the expected ones.
- **Workflow:**
  1. Select a scenario.
  2. Run it. The timeline is data, not code.
  3. The user acknowledges each alarm.
  4. Read the debrief.
  5. Export it as a PDF training record. The record is stored in Supabase only when signed in.
- **Value:** It turns a decorative cockpit into an operator-training tool. That fits the owner's operations background and the ACCURACY rule.
- **Technical implementation:**
  - `data/scenarios/*.json` holds steps of {t, event, state deltas}.
  - The engine thermal model drives temperatures.
  - The existing alarm UI is reused.
  - A seeded clock makes runs reproducible.
- **Integration points:** datahall, datahallAI, fuel-system, EPMS, the incident dossiers (a scenario can cite an incident).
- **Complexity:** Medium
- **Effort:** 4 weeks (score 5)
- **Impact:** 8/10
- **Innovation:** 8/10
- **Confidence:** 7/10
- **Dependencies and risks:** The thermal rates must come from the engine and be sourced, not tuned for drama. **Major feature: needs owner approval.**
- **Acceptance criteria:**
  - The same scenario and seed give byte-identical state traces (gate).
  - `Math.random` is absent from the cockpit alarm path (grep law).
  - Every scenario cites its basis.
  - The debrief lists each alarm with expected and actual timing.

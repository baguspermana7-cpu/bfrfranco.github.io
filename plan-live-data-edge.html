Stay static, or add one edge function?

RZ is 100% static on GitHub Pages — fast, free, durable. But that ceiling is exactly what blocks the most-wanted upgrades: live data, a strict CSP, and server-side auth for the Maintenance Workbench. One small edge function (a Cloudflare Pages Worker) unlocks all three at once. This deck weighs static vs edge — and answers the ECC plan's open question Q3.

02 The static ceiling

Three things RZ can't do — because it's 100% static.

GitHub Pages serves files; it runs no code server-side. Everything below is blocked by that single fact. None is a content problem — they're all the same platform wall.

Live datacalculators hardcode 2025 figures — no way to pull live grid / energy / weather safely (CORS + key exposure)blocked
Strict CSPinline styles/scripts on ~120 pages — can't ship a nonce'd Content-Security-Policy header (Pages sets no headers)blocked
Server RBACworkbench auth is client-side only — no tenant/role/asset scoping can be enforced; anyone can read the JS gateblocked
Static sitefast · free · durable · zero-ops — the thing we do not want to losekeep

The question isn't "static or not" — it's how little server we can add to unblock these three without giving up the static benefits.

03 One worker, four unlocks

How one edge function changes the request.

Click a node. Today the browser hits a static file directly. Add a tiny edge worker in front and the same request gains a place to run code: fetch live data with a hidden key, inject a CSP nonce, check a real auth token, and cache — all before the HTML reaches the user.

The worker

Edge Worker — one small function

A single Cloudflare Pages Worker sits in front of the static origin. It runs ≤50 lines of code per request: it can fetch external APIs with a secret key, rewrite the response to inject a CSP nonce, validate an auth token, and read/write a KV cache — then pass the static HTML through untouched. The site stays static; the worker is the only moving part.

04 What one worker unlocks — click a capability

One function, four walls gone.

Each capability is blocked today purely because GitHub Pages is static — there is nowhere to run code between browser and file. Each panel shows what exists today, what to build (real files), and the first proof. Tap a tab.

Live data with a hidden key EDGE · fetch

RZ calculators run on pinned 2025 figures — accurate at ship, stale forever after. A browser can't call most data APIs directly: CORS blocks it, and any API key shipped to the client is public. The worker fetches server-side with a secret, caches the result, and falls back to the pinned dataset offline.

TodayEvery calculator hardcodes a 2025 dataset. No way to pull live grid carbon, energy price, or weather without exposing a key or hitting CORS.
BuildWorker route /api/data/:metric calls the upstream API with env.API_KEY, writes the response to KV with a TTL, returns it with a freshness header. Client js/rz-data-layer.js reads it and falls back to the pinned JSON if the route is unreachable.

Strict CSP via per-request nonce EDGE · headers

A strict Content-Security-Policy is the single biggest hardening win — but it forbids inline <script>/<style> unless each carries a matching nonce. ~120 RZ pages have inline code. Extracting it all is a months-long refactor; a worker injects a nonce at the edge instead.

TodayNo CSP (or a loose one). Inline scripts/styles everywhere mean a strict policy would break the whole site until every page is refactored.
BuildWorker generates a random nonce per request, rewrites inline tags to nonce="…" via HTMLRewriter, and sets Content-Security-Policy: script-src 'nonce-…'. Zero page edits; the static HTML ships untouched.
Proofsecurityheaders.com grades A+; an injected <script> without the nonce is refused by the browser.

Real server-side RBAC EDGE · auth

The v1.41.x workbench gates pages by tier/role — but a client-side gate only hides content; the file is still on the origin and fetchable by URL. Genuine access control has to happen before the bytes are served. Only a server can do that.

TodayAuth is enforced in JS (enforceTierFeatureAccess). Bypassable by anyone who requests the raw HTML directly — fine for soft-gating, not for anything sensitive.
BuildWorker validates a signed session token (HMAC/JWT) and checks tenant · role · asset scope against the page's access entry before proxying the origin file. Unauthorised → 302 to login, never the content.
ProofA free user requesting a pro workbench URL directly gets redirected, not the file — the gate is real, not cosmetic.

Edge cache & resilience EDGE · KV

The same worker that fetches live data also makes the site faster and tougher: cache hot responses in KV at the edge, serve stale-while-revalidate when an upstream is slow, and degrade gracefully to the pinned static data when everything else fails. The worker is purely additive — remove it and the site is exactly what it is today.

TodayStatic files are already fast + durable on GitHub Pages. But there's no shared cache for live values, and no server layer to absorb an upstream outage.
BuildKV namespace per metric with TTL + stale-while-revalidate; a tiny purge route for manual invalidation. Every cached value carries source · fetched-at · ttl so the freshness chip is honest.
ProofUpstream API down → calc still renders last-good value + "stale 6m" chip, never an error. Worker removed → site degrades to today's static behaviour.

08 Open for discussion

Decisions this plan needs from you.

Four questions whose answers change the build. Answer them and the roadmap converges to a chosen path — each is left open below for your verdict.

Q1 · PLATFORM

Stay static, or add one edge function?

The core call. Live data, a strict CSP, and server-side RBAC all hit the same wall — GitHub Pages runs no code. One small Cloudflare Pages Worker unlocks all four at once, leaves the static files unchanged, and is fully reversible. Worth one moving part, or keep everything client-side with cached fallbacks?

□ DECISION — awaiting your answer (A / B / C)
Q2 · TRIGGER

Which wall justifies the worker first?

If you go B, one unlock leads. Live carbon/energy data is the most visible (calculators stop being frozen at 2025); a real CSP grade is the biggest hardening win; genuine workbench RBAC is the one a client-side gate can never fake. Pick the lead and the rest follow on the same worker.

□ DECISION — awaiting your answer (live data / CSP / RBAC)
Q3 · HOST

Cloudflare, or another edge runtime — and does the origin move?

Cloudflare Pages Workers + KV is the assumed default (generous free tier, HTMLRewriter for the nonce). Netlify/Vercel edge are alternatives. Separately: keep the static origin on GitHub Pages and put the worker in front, or move hosting to Cloudflare Pages entirely?

□ DECISION — awaiting your answer (CF / other · origin stays / moves)
Q4 · AMBITION

One function, or a full edge platform?

Option B is a single ≤50-line worker — the minimal unblock. Option C productises it: KV observability, the workbench RBAC as a real product surface, request analytics. Same four unlocks; C is a later call once the worker has earned its keep.

03

Why a naive merge hurts — but the real surface is small

A straight git merge ft-phase2 estimates ~428 hunks, which sounds brutal. But a file-level dry-run (read-only, measured live) shows the actual conflict surface is tiny: 52 of the 65 files land conflict-free, and most of the 13 conflicts are auto-regenerated build artefacts, not hand-merges.

52 files · land clean no conflict

Net-new, ft-phase2-only — no counterpart on main, apply additively with zero conflict: the Maintenance Decode Lab + engine (js/maintenance/*), the Workbench prototype, all docs/contracts/* schemas, the 6 audit tools, the depth-passed pillar-* pages, fixtures, OG images.

13 files · conflict mostly auto

8 just regenerate — changelog.html, llms.txt, llms-full.txt, search-index.json, sitemap.xml (re-run the build tools); js/rz-version.js (take main's higher number), sw.js + CHANGELOG.md (mechanical append). Only ~5 are real content merges: FF-1, FF-2, geopolitics-3 (edited on main this session for the amber refine), datacenter-solutions, network-visualization-hub.

So the honest effort is land 52 clean → regenerate 8 → hand-merge ~5 content pages. That's what makes Option A below realistic in a session or two, not the merge nightmare the raw hunk count implies.

04

Five ways to reconcile

Ordered roughly safest → fastest. The split between "clean net-new files" and "conflicting shared files" is what makes a hybrid attractive.

A · Cherry-pick the clean wins safest

Land the net-new, conflict-free work first (Decode Lab, Workbench prototype, the 5 audit tools, AI-Maint pages), then hand-port the pillar/standards depth passes as fresh edits on main. Drop nothing of value; never fight a 428-hunk merge.

+ low risk · incremental · each piece gated– manual · several sessions

B · Rebase ft-phase2 onto main linear history

Replay the 12 commits on top of current main. Keeps authorship + a clean linear log, but you resolve conflicts 12 times (once per commit) across the overlapping files.

+ clean history · preserves commits– 12× conflict passes · easy to mis-resolve

C · One merge commit fastest

A single git merge ft-phase2, resolve all ~428 hunks once, ship as one reconciliation commit. Fast to start, but the big simultaneous conflict resolution is the highest-risk single step.

+ one operation · done in a day– 428 hunks at once · regression-prone

D · Re-port feature-by-feature cleanest result

Treat ft-phase2 as a reference, not a source. Re-apply each v1.41.x feature freshly on main, using the branch as the spec. Slowest, but the result matches current main's conventions exactly.

+ no merge debt · matches current code– most effort · loses original commits

E · Abandon ft-phase2 last resort

Declare main canonical and salvage only a few specific files by hand. Only sane if the v1.41.x work is judged superseded by the v1.42–43.x BMS direction.

+ zero merge work– loses Decode Lab / Workbench / pillar depth unless re-done

Recommendation (mine, not a decision): A then D — cherry-pick the conflict-free net-new files immediately (instant value, zero risk), then re-port the pillar/standards depth as fresh edits. It avoids the 428-hunk merge entirely and ends with main fully current. But the verdict is yours below.

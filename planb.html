How this works

The convention every plan page follows

So plans stay comparable and decision-ready no matter which session authored them.

RULE 01

One topic per page

Each plan is a standalone HTML page scoped to a single subject (e.g. ECC adoption). The hub never holds plan content itself — only links.

RULE 02

Always show options

Every plan presents 2–4 distinct options (e.g. minimal / standard / full), each shippable on its own, with cost + risk + "who it's for".

RULE 03

Always show examples

Abstractions are cheap. Every plan includes concrete artefacts — code snippets, real shapes — so it's judged on output, not vocabulary.

RULE 04 ★

Always show a visual mockup

Every plan renders a proper layout mockup of what the thing looks like — a CSS-rendered preview (console, flow, panel), not only code or text. Show the surface.

RULE 05 ★

Every change = before vs after

Any proposed change shows a side-by-side before / after — each side with its visual snippet and code and a one-line explanation. Three together, never one alone.

RULE 06

End with decisions

Each plan closes with the open questions whose answers change the build, so a discussion can converge to a chosen path.

RULE 07

Instrument aesthetic

IBM Plex Sans + JetBrains Mono, signal-amber / oscilloscope-green / instrument-cyan / fault-red, thin lines, dark canvas. No AI-slop.

RULE 08

Internal & noindex

Plan pages are working surfaces: noindex,nofollow, not in the sitemap. Promoted to standarization/ + memory once agreed.

Adding a new plan

The repeatable recipe so any session produces a hub-consistent plan page.

  1. Create plan-<topic>.html in the site root — copy plan-ecc-adoption.html as the structural template (same CSS tokens, topbar with ← Hub link, badge row).
  2. Scope it to one topic. Sections: Recognition/Context → core analysis → Options (2–4) → Examples (code) → Visual mockups (rendered layouts) → Before/after (visual + code + explanation per change) → Roadmap → Effort×Impact → Open Questions.
  3. Visual is mandatory (Rules 04–05): every plan must render at least one layout mockup, and every change must show before/after with all three — visual, code, explanation. Reuse the .mock / .ba CSS from plan-ecc-adoption.html.
  4. Register it: add a .plan card to the registry above (flip a reserved slot to live, or add a new card).
  5. Keep it internal: <meta name="robots" content="noindex, nofollow">, do not add to sitemap.xml / llms.txt / nav.
  6. Promote on agreement: once a plan's option is chosen, fold the decision into standarization/ + memory, and let the build track (versioned ships) execute it.

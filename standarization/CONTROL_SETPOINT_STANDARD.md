# CONTROL_SETPOINT_STANDARD — setpoints, references and limits on the cockpits

Owner request R187 (2026-11-22): every setting, setpoint or threshold, and its current value, must be visible,
on the trend as a line and in the double-click modal. PRD: `documentation/prd/PRD_SETPOINT_SIM.md`.

## 1. One registry

`data/control-points.json` is the only place a setpoint lives. It is GENERATED by
`node tools/build-control-registry.mjs --apply` from:

- the Conventional limits registry (`data/conv-parameters.json` `limits`),
- the DC AI point records (`js/datahall-ai/points.js`),
- the curated file `data/control-points.curated.json` (setpoints held by an engine parameter, plane controllers,
  value evidence).

The same command writes the browser twin `js/rz-control-points.js` (`window.RZControlPoints`). Never edit
either output by hand. A page never types a setpoint, a reference value or a limit.

## 2. Setpoint or reference

- **setpoint**: a controller holds it. Exactly one equipment class per value: the CDU holds TCS supply, the dry
  cooler its leaving water, the chiller CHW supply, the CRAH supply air and humidity, the dosing and blowdown
  controllers the water chemistry.
- **reference**: the same value read anywhere else (a manifold, a rack), a nameplate, a nominal or a design value.
  A reference row names the class that holds it (`heldBy`).
- A band's `nominal` is the middle of a band, never a setpoint.

Law C9 (`tools/test-control-registry.mjs`) fails a value held by more than one class.

## 3. Every value names its source

Each setpoint carries an evidence class (MEASURED, STANDARD, ADOPTED, DESIGN, DERIVED, ASSUMED) and a source. A
typed value with no source of its own is ASSUMED and says why. A setpoint is adjustable only when a written basis
gives the range (rack inlet 18–27 °C: ASHRAE TC9.9 class A1; secondary DP 60–140 kPa: the chiller-plant page
range). Otherwise it is fixed, and the modal says what fixes it.

- On a phone (≤ 600 px) the modal table keeps Setpoint, SP, Live and Error. The rest moves into the row's

- The SP label is never coloured by state and never repeats the unit the axis already carries.
- A what-if shows steady state only. Every what-if note says the dynamics are not modelled, and says what the engine does

### 4a. Sequences (P3)

- A sequence is data: `data/sequences/<class>.json`, built by `node tools/build-sequences.mjs --apply` into
  `js/rz-sequences.js`. Its structure follows ASHRAE Guideline 36-2021 (chilled-water plant, from RP-1711); its numbers
  never do.
- A condition never types a threshold. `limit` + `band` reads the conv limits registry, `param` reads the engine
  snapshot, `derived` is a plant quantity the builder computes from the snapshot (`demand_pct`,
  `part_load_n_minus_1_pct`, `available_capacity_margin_kw_th`, formulas in the twin). A delay, hysteresis or stagger that
  no source in the repo states is listed in the mode's `assumed` map with its reason, and the modal prints "(assumed)".
- A sequence names its `fleet`: the engine keys of running units, installed units, the unit rating and the load (one key,
  a difference or a product), the noun and unit for the table, and the PV that answers a shortfall (CHW supply rises,
  header DP falls, CDW supply rises). A condition may also name a registry setpoint (`setpoint`: control registry id).
- A scenario is a list of steps (`mode` + what changes: running ±1, available ±1, running to zero, restart all). The
  builder walks it on the engine's plant quantities: capacity = running × unit rating, part load = min(100 %, load /
  capacity) because a unit cannot run above its rating, capacity short = load − capacity, the PV moves exactly while
  capacity is short. These are steady states; how fast the plant gets there is not modelled.
- A fleet quantity is one snapshot key, a difference, a ratio (the UPS share of one hall = system rating / halls, so
  the sequence speaks the same unit as the EPMS sheet it opens on), a product (the generating set's usable unit = rating × maximum
  loading; the table then heads its column "Load / usable" and the note shows the product), or a count of the engine's
  unit-state table (`count: { kind, hall, state }`). A standby supply names `source: "utility"`: a step's `source`
  says who carries the load (`utility` = short 0, none of the units loaded; `gen` = the units carry it; `none` = nothing
  does, the whole load is short), the table gets a "Load on" column, and part load shows only while the units carry the
  load. `running: "duty"` = available − the fleet's `spare` key, `"all"` = every available unit. The generating-set
  sequence follows the fuel cockpit's own rule (duty sets = count − spare carry the hall's facility load; the spare
  stays on standby).
- What the plant model does not hold is said, not filled in: no thermal storage in this plant (no TES discharge step),
  pump ride-through on UPS and the chiller's rapid-restart time are not modelled.
- The path figure stays inside the RZDiagram budget of 9 nodes: it draws the scenario's modes, the full list of modes is
  the text list under it.

### 4b. Control loops on the P&ID (P4)

- A loop lives in the curated setpoint row (`loop`: tag, sheet, kind PI/staging/reset/interlock, action direct/reverse,
  pv {tag, node or draw, what}, mv {classKey, what}, tuning or tuningNote, basis). The builder refuses a loop without
  them, and a loop with no sheet must say why (`notDrawn`: the rack-inlet reset has no P&ID on the data hall page).
  The twin answers `RZControlPoints.loops(sheetId)`.
- The sheet draws what the registry lists for it and types no tag: a controller is an ISA-5.1 `instPanel` bubble (shared
  BMS function), its PV instrument an `instField` bubble, joined by dashed signal lines (`w: 'signal'`); impulse lines
  are `w: 'inst'`. A bubble carrying four letters is drawn at size 44 so the letters (8.5 px) sit inside the circle.
- The bubble shows `SP` (registry; the operator's value in MAINT) and `OUT` (the engine's mean drive speed of the running
  units). No tuning is invented: `tuningNote` says "not modelled" until a source gives gain and time.
- A PV the plant does not measure separately reads the engine's steady state, which holds the setpoint, and says so
  (PDT-01 remote DP = the DP setpoint in force). Never bind it to a different quantity: the chiller-plant KPI "Header
  DP" averages the primary loops' authored DPS1/DPS2 and is not the remote DP the secondary pumps hold.
- A double-click on a controller opens the modal of the equipment it drives; the Setpoints block names the loop
  (`[data-rz-cvm-loop]`: PV → controller → MV, action, tuning, basis). Pointer or focus on any loop member marks the
  whole loop (`data-loop` = registry setpoint id on nodes and signal lines, class `.is-loop`, js/rz-hmi-sheet.js).
- **Unit loops (P4b).** A loop held inside one machine names the inside view as its sheet (`int-<class>`, a file
  `js/conv/internals/<class>.js`; the builder refuses another name) and its PV and MV as node ids of that view
  (`pv.node`, `mv.node`). The internals file draws the loop only when the twin lists it: TIC-CHWS on the chiller
  (TT-CHWS at the CHWS outlet nozzle → TIC-CHWS → VFD; SP = `cooling.chws_c`, OUT = `cooling.chiller_speed_pct`) and
  TIC-SAT on the CRAH (the supply-air TT → the unit controller, retagged → the chilled-water valve; SP =
  `cooling.crah_supply_air_c`, OUT = `cooling.crah_valve_open_pct`, the coil flow over its design flow). A cooling
  loop is **direct** acting (temperature up, capacity or valve up). The valve's stem position stays "not modelled";
  its opening as a flow ratio is the engine's.
- **One block (§C4).** `js/rz-sp-block.js` (`RZSpBlock.inner(rows, {snapshot})` + `bind(host, {recompute, live})`) is
  the only writer of the Setpoints & limits markup; the conv modal frames it in its section and passes
  `CONV_CALC.recompute` and its page-or-engine live reader; the DC AI inspector (P5) passes `DCAI_CALC`. Every page that
  loads `js/conv/equipment-modal.js` loads it after `js/rz-control-points.js`. Gate C14 (`test-control-registry.mjs`).
- **Authority (P10).** Every drawn loop names the engine key of its output (`out.key`, optional `out.minKey`; the
  builder refuses a drawn loop without it). `RZControlPoints.authority(loop, snapshot)` = { out, left = 100 − out,
  min, sat, band }: saturated within 2 % of 100 % or of the minimum (band ASSUMED, the one rule; never re-typed in a
  page). The modal's loop line says `OUT · authority left` and **SATURATED** with what it means; an inside-view bubble
  appends `· SAT` to its OUT. The word is used, never a glyph: ◆ is the alarm glyph of `js/conv/point-status.js`.
  Measured: PDIC-01 98.7 % (1.3 % left) and TIC-SAT 99.5 % (0.5 % left) saturated; TIC-CDWS and TIC-CHWS 89.3 %.
- **DC AI loops (P10 part 2).** `dcaiLoops` in `data/control-points.curated.json` gives a DC AI setpoint its loop; the
  builder refuses an id that is not a point, a loop on a reference value, and an `out.key` that is not a number in
  `DCAI_CALC.snapshot`. TIC-nn1 (CDU, drawn on DH-M-103: TT-nn3 → TIC-nn1 → TV-nn1) acts on
  `equipment.cdu_fws_valve_pct`; TIC-SA (fan wall, not drawn: the FW-nn sheet has TT-nn2 and TV-nn, no controller) on
  `equipment.crah_chw_valve_pct`, both the engine's equal-percentage stroke (A8a). `authority()` rounds OUT to 0.1 %
  before the rule. Measured at design: CDU valve 99.6 % (0.4 % left), fan-wall valve 99.9 % (0.1 % left), both
  SATURATED: at the design point neither unit has valve travel left for more heat. Gate D11 of `test-dcai-setpoints.mjs`.
- **Step strip (P8, fallback before the rz-trend overlay hook).** `RZConvSequence` 1.1.0 draws, under the steps table,
  one small multiple per quantity (≤ 4): DC AI engine sweeps plot their engine results, a conventional sequence plots
  running units, part load and shortfall (a series with a missing value in any step is left out). One point per step,
  revealed with its table row; the line between points is dashed; x axis "step 1 – N" (never a time unit: dynamics are
  not modelled); y labels are the series' min and max; caption "SIMULATED · steady state per step · dynamics not
  modelled"; Reset hides the strip. No animation, so reduced motion needs no branch. Laws S7d / S7e / S7g.
- **Loops table (P10 part 3).** `RZSpBlock.loops(rows, { snapshot })` is THE compact table of the loops a page owns:
  Loop · SP · Live · Error · OUT · Left · State (`holds`, `◆ saturated`, `OUT not modelled`). Rows come only from
  `RZControlPoints.loopRows(cockpit, sheets)` (twin 1.4.0): every registry setpoint whose loop is drawn on one of those
  sheets or inside those machines, so a new loop in the registry appears without a page edit. Live / Error are filled by
  `RZSpBlock.bind` like the setpoint rows. Conventional pages mount it with `<div data-rz-loops-host data-sheets="…">` +
  `js/conv/loops-card.js` (chiller-plant: CH-M-101, CH-M-102, int-chiller → PDIC-01, TIC-CDWS, TIC-CHWS; datahall
  inspector: `int-crah none` → TIC-SAT and TIC-RI, `none` = a loop with no drawing, OUT not modelled); in a 344 px
  column it hides Error, and SP below 600 px, keeping both in the cells. The DC AI inspector puts it at the top of its
  Setpoints block (Loop · Live · OUT · Left · State). Gates S11c (`test-setpoint-sim.mjs`) and D12 (`test-dcai-setpoints.mjs`).
- **Reset (cascade) loops.** A `kind: 'reset'` loop names the loop whose setpoint it writes (`slave`, an existing
  registry tag; the builder refuses another). TIC-RI (rack inlet) resets TIC-SAT: contained aisle, no mixing modelled,
  so the slave setpoint equals the master's.
- **Loops table under a word budget.** Where a page's word budget is spent (datahall T2 120), the table sits in a
  `<details>` whose summary is an icon named by `aria-label` + `title` ("Control loops"). `loops-card.js` builds the
  table only while the details is open, because a closed `<details>` keeps layout boxes and its text counts as visible.
- **A controller bubble's inspector (v3.115.1).** A bubble with `ctrl: <node id>` opens with Open equipment HMI on that
  unit. Its Alarms are the limits of the process value it holds, from the limits registry by the id the controlled
  unit prints (`values[].limitsOf || point`; LIC-A3 → `fuel-system.DT.level_pct`, 45 / 25 %). Never borrow the unit
  CLASS's alarms or trend: a class can be shared by different vessels (day tank and bulk tank are both
  `fuel:tankStorage`; v3.115.0 showed the bulk 85 % trend on a 90 % day tank).
- **A modulating page loop (v3.115.2).** A page setpoint with `kind: 'modulating'` may carry a PI / PID loop. That
  loop names its transmitter node (`pv.node`) and its driven unit (`mv.node`), both on the sheet. It has no cut-out,
  no sourced tuning (`tuningNote` says so) and no engine output, so OUT reads "not modelled". The page's simulated PV
  is the setpoint at steady state. PIC-301 (WT-M-101) holds PT-301 at `conv.water-system.booster_discharge_sp`
  through the duty booster's speed. The signals run PT-301 → PIC-301 → P-301A. On-off loops still sit only on the
  cut-in that starts their unit. Gates: T3 and S8e water in `test-typed-control-numbers.mjs`.
- **A bubble says its tag once (v3.115.2).** The sheet engine names a node "<tag> — <label>", so a controller's
  `label` never starts with its tag: write "P-301A pressure controller (reverse acting PI)", not
  "PIC-301 — …". Gate S8f. The payload kind of a bubble (`n.loop`, no class) is "Controller". A value a bubble prints
  from the registry (`values[].const`) is declared, never SIM (`test-conv-payloads` P11).
- **One vessel symbol, two classes (v3.115.2).** `classOf` gives a day tank (`fuel`, `tankStorage`, `dt<k>`) the class
  `fuel:dayTank`, whose rows read the limits registry (`L(label, id, key)`, key lo_warn / lo_alarm / hi_* /
  nominal) instead of the bulk tank's parameters. A trend with `lim:` takes that row's nominal as its reference
  (P10).
- **A controller on a hand-drawn P&ID (v3.116.2).** A page whose drawing is not on the sheet engine (cdu-mini-bms)
  still takes its controllers from the registry: `loop.sheet` names the drawing (`cdu-pid`), and the page draws one
  ISA-5.1 panel bubble per loop with `data-loop="<tag>"`, its setpoint printed under it from the registry, and dashed
  `path.sch-sig` signal lines from the transmitter and to what it drives (`data-tag` on the driven symbol). No other
  `data-loop` bubble may exist on that drawing. Gate: S8e cdu in `test-typed-control-numbers.mjs`.

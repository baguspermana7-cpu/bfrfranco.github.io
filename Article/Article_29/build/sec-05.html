Mixture of Experts: big brain, small bill

In a mixture-of-experts (MoE) model, the single feed-forward network of each block is replaced by many smaller ones, called experts, plus a small router. For every token the router picks a handful of experts and the rest stay idle. The model can hold far more knowledge than it computes with on any one token. The price is paid elsewhere: all experts must sit in memory, and tokens must be shipped between GPUs to reach them.

5.1 Routing and load balancing

DeepSeek-V3 is the best documented example [S1]. Every layer except the first three is an MoE layer with one shared expert (always on) and 256 routed experts, each with an intermediate width of 2,048. The router computes a sigmoid affinity s_i = σ(u·e_i) between the token vector u and each expert’s centroid e_i, takes the top 8, and normalises the gates over the selected experts. Each token may be routed to at most 4 nodes, which caps cross-node traffic.

The hard part is balance. If the router favours a few experts, those GPUs saturate while others idle. Earlier MoEs such as Switch Transformers [S59] added an auxiliary loss to push the load flat; the DeepSeek authors report that a large auxiliary loss “impairs the model performance” [S1]. Their alternative is an auxiliary-loss-free bias: each expert carries a bias b_i that is added to its score only when choosing the top 8, never in the gate weights. After each training step, b_i is lowered by a small step if the expert was overloaded and raised if it was underloaded. A tiny sequence-level balance loss remains as a safety net.

5.2 Total versus active parameters

The result for DeepSeek-V3 is 671B total and 37B active parameters [S1], so 37 / 671 = 5.5% of the weights work on a given token (derived). Per-token compute is 2 × 37e9 = 7.4e10 FLOP, against 2 × 671e9 = 1.34e12 for a dense model of the same size, a factor of 18 (derived). Other published MoE models follow the same pattern:

Each number buys something different. Memory is set by the total: 671B parameters in FP8 is 671 GB, which fits an eight-GPU H200 server (8 × 141 = 1,128 GB, derived from [S9]) but not a single card. Compute per token is set by the active count. Bandwidth sits between them. At batch size 1, only the active experts’ weights are read per step, so decode is fast. At a large batch, different tokens select different experts, so almost all experts are touched on every step and the bandwidth demand moves back toward the total [S1]. An MoE is therefore cheapest per token at high batch and in compute, and dearest in HBM capacity.

5.3 The network bill

Placing different experts on different GPUs is called expert parallelism. Every MoE layer then needs an all-to-all exchange: each token’s vector is sent to the GPUs holding its chosen experts and the results are sent back. This happens twice per layer, for every layer. DeepSeek-V3’s production decode unit spans 40 nodes, 320 GPUs, with one expert per GPU plus 64 GPUs for redundant and shared experts [S1]. The cap of 4 nodes per token exists to limit exactly this traffic.

The consequence for the facility is that an MoE service is a networking workload as much as a compute one. The experts live on NVLink within a node and on InfiniBand or RoCE between nodes, so the fabric has to be sized and cabled as part of the compute, not added afterwards. A 671B MoE is also not a “smaller” deployment than a dense 405B: the dense model needs fewer GPUs for its weights, the MoE needs fewer FLOPs per token, and which one is cheaper depends on batch size and on the interconnect.

Operator takeaway

Read an MoE spec sheet in two columns. Total parameters tell you how many GPUs must hold the model. Active parameters tell you what each token costs in compute. The gap between them is paid for in interconnect.

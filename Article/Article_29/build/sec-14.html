Agents and harnesses

A model on its own only produces text. An agent is that model placed inside a loop: it proposes an action, ordinary software carries the action out and reports the result, and the model decides what to do next. The software around the model is the harness, and it, not the model, decides what is allowed to run, what gets checked and when to stop. For an operations team the practical point is that an agent turns one question into dozens of model calls, so cost, latency and security all multiply.

Tool calling, ReAct, workflows and agents

In tool calling the model emits a structured request, typically JSON with a function name and arguments. The harness executes it and returns the result as a new message. The model never runs code itself. ReAct showed the value of interleaving reasoning, action and observation: on the ALFWorld and WebShop tasks it beat imitation and reinforcement-learning methods by 34 and 10 absolute points, using one or two in-context examples [S42].

Anthropic's guidance draws a line that is useful for scoping: “Workflows are systems where LLMs and tools are orchestrated through predefined code paths. Agents are systems where LLMs dynamically direct their own processes and tool usage.” Its patterns are prompt chaining, routing, parallelisation, orchestrator-workers and evaluator-optimiser, and its advice is to start simple and to design the agent-computer interface as carefully as a human interface [S62]. A fixed workflow is cheaper and easier to test; reach for an agent only when the steps cannot be known in advance.

The Model Context Protocol

MCP standardises how a model application connects to tools. It uses JSON-RPC 2.0 between hosts (the LLM application), clients (connectors) and servers. Servers expose resources, prompts and tools, and clients may offer elicitation, where the server asks the user for input. The version read for this article is the 2026-07-28 revision. Its security principles are user consent and control, data privacy and tool safety. It states that tools “represent arbitrary code execution” and that tool descriptions are to be treated as untrusted unless the server is trusted [S61].

Designing the harness

The model proposes; the harness disposes. A working checklist, drawn from the vendor guidance cited above [S61][S62]:

  • Context. Keep a small, clear set of tools with explicit schemas. Manage the window with summarisation or compaction, give sub-agents their own windows, and cache the stable prefix. Memory is the window itself, a retrieval store, or notes persisted to files.
  • Verification. Check results with tests, linters or an evaluator, not with the model that wrote them. A model grading itself shares its own blind spots.
  • Sandbox. Run tools in a container with no secrets and controlled network egress.
  • Budgets. Cap steps, tokens and wall-clock time.
  • Approval. Require a human to confirm irreversible actions.
  • Logging. Record every call so a run can be replayed.

Multi-agent designs, in which an orchestrator hands separable subtasks to parallel workers, spend tokens in proportion to the number of agents. Anthropic's advice is that this pays only when the subtasks are genuinely independent [S62].

With an assumed 0.5 s TTFT and 20 ms per token, each step takes 0.5 + 800 × 0.02 = 16.5 s and the run about 8 minutes. The rates in the latency line are assumptions. The lesson for capacity planning is that prefix caching, covered in the serving section, is worth more to an agent than to a chat, because the same long prefix is re-sent at every step.

Failure modes

  • Hallucination. The sampler always produces some plausible continuation, so claims must be checked by tools or retrieval.
  • Prompt injection. Instructions hidden in a web page, file or tool output can redirect the agent. MCP's specification treats tool descriptions as untrusted [S61]. Mitigations are least-privilege tools, human confirmation and isolating untrusted content.
  • Loops and drift. The agent repeats a call or forgets the goal. Step and token budgets and progress checks contain it.
  • Over-trust in self-verification. Use external checks, such as test suites.

Evaluating agents

SWE-bench consists of 2,294 real GitHub issues from 12 Python repositories. At its launch the best model, Claude 2, solved 1.96% [S58]. On the official SWE-bench Verified leaderboard data, read on 2026-10-16, the top entry is 79.2% (Claude 4.5 Opus with two different agent scaffolds, December 2025), followed by 78.8% and 77.4% [S22]. Higher figures for 2026 models circulate in vendor and aggregator material but do not appear on the official board, so this article does not quote them. Vendor-run examples: gpt-oss-120b at 62.4 with high reasoning effort [S24], and Kimi K2 at 65.8 [S25].

GAIA poses 466 questions that real assistants face; humans score 92% against 15% for GPT-4 with plugins in the 2023 paper, and answers to 300 questions are withheld for the leaderboard [S43]. Current GAIA leaderboard values could not be read and are not quoted.

Scores from different sources disagree for four reasons: contamination of training data with test items, saturation of an old benchmark, dependence on the agent scaffold (the same model scores differently under different harnesses, visible within the official board itself [S22]), and the difference between pass@1 and pass@k.

Treat every tool result as hostile input

Give an agent the fewest tools and the least privilege that finish the job, run them in a sandbox without secrets, and require a person to approve anything irreversible. If an agent can read a web page and also run a command, a hidden instruction on the page can run the command.

When to use an agent, and how to build one

The engineering question is where a probabilistic component belongs in an otherwise deterministic system. The evidence gives one answer: let the model do what only a model can do (read untidy input, choose among options, draft) and put every consequence behind a check that does not rely on the model. Below: a decision table, a reference architecture, a worked example, and run budgets.

9.1 Agent, hybrid or script: decision table and scorer

Decision table. Source: dossier synthesis of [S14] [S33]; an engineering judgement and not a standard.

The scorer below puts the table into numbers. Five inputs from 1 to 5: variability of input (V), cost of an error (E), verifiability (Vf), frequency (F) and latency budget (L). Weights are the author’s design choices: a judgement aid, not a measurement.

N     = (V − 1) / 4
Risk  = ((E − 1) / 4) × (1 − (Vf − 1) / 4)
Lp    = (5 − L) / 4
Score = 100 × N × (1 − Risk) × (1 − 0.5 × Lp)

A score below 35 means script or workflow; 35 to 65 means hybrid (the model classifies, extracts or drafts, code validates and executes, a person approves side effects); 65 or above means an agent loop with verifiers. Hard overrides apply afterwards: with E = 5 and Vf ≤ 2 no autonomous action is allowed, in line with the CISA principle on human oversight [S33]; with L = 1 the path is real-time and not an LLM; with V ≤ 2 the answer is a script. Worked check for a BMS alarm-triage summary (4, 4, 3, 5, 3): N = 0.75, Risk = 0.75 × 0.5 = 0.375, Lp = 0.5, so Score = 100 × 0.75 × 0.625 × 0.75 = 35.2, a hybrid, just. A chiller setpoint write (3, 5, 2, 4, 2) scores 7.8 and trips the first override.

9.2 Reference architecture: probabilistic planner, deterministic executor

Six parts in a line: A probabilistic planner (the LLM) proposes an action. A typed tool interface validates it against a schema and an allow-list. Deterministic executors (scripts, APIs, compilers) carry it out. Verifiers (tests, linters, type checkers, simulators, policy checks) judge the result. A human gate stands in front of irreversible actions. An audit log records everything. Budgets on steps, tokens, time and cost are enforced outside the model. The model never holds credentials directly and never writes to safety-rated systems [S14] [S31] [S32] [S33]. Anthropic on the verifier: the agent should get “ground truth from the environment at each step” [S14].

The seam between the halves: the model sees and produces text; the interface turns that text into a typed call or rejects it with a reason that goes back to the model; the executor and verifier produce facts. The model’s explanations of what it did are kept out of the chain of evidence.

9.3 Worked example: a software factory pipeline

The author runs a local (unpublished) pipeline for software changes that applies these rules; facts below were read from its skill file and command-line source on 2026-10-16 [S60]. The roles are an orchestrator on a frontier model; a spec-writer; a builder; four reviewers working in parallel (security, code, UX, UI), where the UX and UI reviewers may answer SKIP only if no user-interface file changed; and an approver. The sub-agents run on a mid-tier model and the approver on a small one [S60].

Every transition is written by a command-line tool into a state file, factory/board.json. The orchestrator is told never to move a job forward on its own reading of a result, but to run the tool and act on its status line. Language models write and judge; exit codes decide [S60].

Review verdicts are parsed by the pattern VERDICT: PASS|FAIL|SKIP; a missing or unparseable verdict is a problem, an invalid SKIP is rejected, and if the code changed after gating the verdicts are stale. The fix loop is capped: max_fix_rounds is 3, at most two fix decisions are allowed per job, and overrides are refused while a hard gate fails. Delivery merges with --no-ff in the job’s worktree, re-runs lint, test and build on the merge result, and pushes fast-forward only, and only if the repository has opted in with "push": true. The human operator’s switches for delivery, push and human review are declared off-limits to the agent [S60].

Demonstrated so far: one job (2026-10-16, a readingTime helper) changed two files; lint and test passed, the build was skipped because none is configured, the other four gates passed, the security and code reviews passed, and the UX and UI reviews were skipped as designed [S61]. No multi-job statistics exist, so per-gate catch rates are unmeasured; the calculator takes them as inputs, and its presets are labelled assumptions.

Not caught by any gate: a wrong specification; tests that encode the same misunderstanding as the code; and blind spots shared by reviewer models from the same family as the generator [S60]. The ladder calculator makes the last point numerically. With five independent gates at 0.60, 0.10, 0.15, 0.50 and 0.50 catch rates, the chance a defect escapes is 0.4 × 0.9 × 0.85 × 0.5 × 0.5 = 0.0765, a coverage of 92.35%. If the LLM review (0.50) shares the generator’s family and its effective catch rate is halved to 0.25, the escape chance becomes 0.4 × 0.9 × 0.85 × 0.75 × 0.5 = 0.11475, a coverage of 88.5%. These values are what-ifs; the structure holds regardless: a defect must pass every rung, so add rungs that fail for different reasons.

9.4 Run budgets: cost, wall clock, context window

Three limits bind an agent run: money, wall-clock time and the context window. Because history is re-read each step, cost grows with the square of the step count. With c0 the starting context, g the tokens added per step and S the number of steps:

input tokens to step S = S × c0 + g × S(S − 1) / 2
Cost(S) = price_in × [S × c0 + g × S(S − 1)/2] / 106 + price_out × S × o / 106
t_step  = TTFT + o × TPOT + t_tool
max_steps = min(S_cost, S_time, S_context)

With defaults of 20,000 starting tokens, 3,000 tokens added per step, 800 output tokens per step, a $5 cap, a 600 s wall clock and 5 s per tool call, at $2 and $10 per million tokens: Cost(10) = $0.75, Cost(20) = $2.10, Cost(30) = $4.05, Cost(40) = $6.60. The cost cap allows 34 steps. One step takes 0.5 + 800 × 0.02 + 5 = 21.5 s (the latency constants are assumptions from Article 29), so the wall clock allows floor(600 / 21.5) = 27 steps. The context limit, compaction at 80% of a 200,000-token window, allows floor((160,000 − 20,000) / 3,000) + 1 = 47. The binding limit is the wall clock, at 27 steps, and a per-step timeout near 65 s (three times the step time) is suggested. Caching changes the slope of the cost curve, not its shape.

Design rules

Use the simplest system that works. Put validation, execution, verification and limits in code. Give every irreversible action a human gate. Add verifiers that fail for different reasons. When an agent’s path for a class of task becomes stable, replace it with a script: a cheap, testable routine.

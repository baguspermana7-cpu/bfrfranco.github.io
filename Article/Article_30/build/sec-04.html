What an agent actually is

An agent is a loop. A program shows a language model the goal and the history so far, the model proposes the next action, ordinary code checks and executes it, the result goes back into the history, and the cycle repeats until a stop condition is reached. In that loop the model does the one thing a conventional program cannot do cheaply, which is to turn untidy input (free text, logs, a screenshot, an error message) into a plausible next step without a rule written for that exact case. Everything else is conventional software. This section describes the division of labour, re-examines the restaurant demo from the video, and places the idea in its history.

Anthropic’s own definition says the same in one sentence: agents “are typically just LLMs using tools based on environmental feedback in a loop” [S14]. The disagreement with the video is therefore not about the mechanism. It is about whether the three non-deterministic rows are worth anything. An analogy from the plant room helps: in a PLC panel the I/O cards do all the physical switching, and nobody concludes that the control logic “did nothing”. The logic decides which output to drive and when. In an agent the model fills that role for inputs that no one wrote rules for. Whether it fills the role well enough is a reliability question, taken up in section 5.

4.2 The restaurant demo, re-examined

Elder’s example of “the LLM did nothing” is OpenAI’s restaurant-booking demo, which he describes as probably a Python program calling probably the OpenTable API (E5, 03:50–05:11) [S1]. He hedges with “probably”, and the hedge was warranted. The demo came from Operator, a research preview announced on 2025-01-23. Operator was “powered by a Computer-Using Agent model, or CUA”, trained “to interact with the front-end of websites, meaning it doesn’t need to use developer-facing APIs”; the model “can use buttons, navigate menus, and fill out forms on a web page much like a human would”, and was “trained to ask for user confirmation before finalizing tasks with external side effects” [S58]. So the booking was not an API script. A vision model read screenshots of a web page and chose clicks (a computer-using agent). Whether OpenTable was a named launch partner I could not confirm; the launch coverage lists DoorDash, eBay, Instacart, Priceline, StubHub and Uber, so the partner claim is unverified [S58].

This matters because the case chosen to show the model contributes nothing is one where the model did the part a script cannot do: perceive an arbitrary page and decide what to do on it. The generic mechanism in his account is correct (section 2). The example does not illustrate it.

4.3 What is old and what is new

“Decades-old automation” (E6, E7) is partly right, and the history shows which part.

  • Agent as a concept. Russell and Norvig define an agent as “anything that can be viewed as perceiving its environment through sensors and acting upon that environment through actuators” (quoted from the textbook, not re-read here) [S21]. By that definition a thermostat is an agent. The word never claimed intelligence.
  • The loop. ReAct (2022) interleaves reasoning, an action and an observation, and is the template for most agent loops today [S18] (see also ReAct, agent loop). Closed-loop control is far older. The new element is the controller, which accepts natural-language state.
  • Tool use and integration. Toolformer showed in 2023 that a model can learn when to call an API [S17]. The Model Context Protocol standardises how tools are described and called over JSON-RPC 2.0; its specification notes that tools “represent arbitrary code execution” [S19] (MCP).
  • Decades old: scheduled scripts, workflow engines, expert systems built from hand-written rules, and RPA, which replays recorded user-interface actions.
  • Not available before roughly 2023: a general component that maps free text, screenshots, logs and error messages to a plausible next action without a rule written for that case. RPA breaks when a button moves. A CUA-style agent may survive the move, and may also click the wrong thing. The trade is flexibility for reliability, and that trade is the real subject of the debate.

On this evidence E7, “decades-old automation”, is partly supported: the executor half is old, the planning half is new. E6, “the LLM did nothing”, is unsupported, since the table in 4.1 lists what the model does, and the harness choice demonstrably changes results, as the Terminal-Bench entries in section 5 show.

4.4 The spectrum: workflow versus agent

Much of the argument over “is it really an agent” dissolves once autonomy is treated as a scale. Anthropic separates two kinds of system: “Workflows are systems where LLMs and tools are orchestrated through predefined code paths. Agents… are systems where LLMs dynamically direct their own processes and tool usage” [S14]. A workflow in this sense has the model fill in steps inside a fixed skeleton. LangChain, in July 2026, describes six levels: hand-written logic, a single LLM call, a chain, a router, a state machine, and an autonomous agent. It grades them by three questions: who decides the output of each step, who decides which step comes next, and who decides what steps are available [S20].

Anthropic’s advice to builders points the same way as the critic: look for “the simplest solution possible… This might mean not building agentic systems at all”, because agents bring “higher costs, and the potential for compounding errors”, and extensive testing “in sandboxed environments, along with the appropriate guardrails” is recommended [S14]. An orchestrator that calls other models is simply another point on the same scale.

What this means for the BMS team

Ask of any proposed “agent” which of the three decisions the model makes: the output, the next step, the set of available steps. If only the first, you are buying a drafting tool inside a workflow, which is easier to test and to bound. Each additional decision handed to the model needs its own deterministic check.

Two of the owner’s counter-claims are covered here. That the model acts as a semantic router or dynamic planner over unstructured intent (C2) is supported [S14] [S20] [S58]. That observe, act and reflect (running tests, reading the error, fixing) is a genuine pattern (C3) is supported as a pattern and only partly as a new one, since ReAct dates from 2022 [S18] and closed-loop control is far older.

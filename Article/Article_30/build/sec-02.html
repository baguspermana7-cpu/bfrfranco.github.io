How a language model produces text and calls tools

The video’s technical core is correct. A language model produces one token at a time, cannot reach the internet by itself, and an “agent” is a program that takes the model’s output, runs something and returns the result. The dispute starts at “did nothing”, tested in sections 3 and 4.

2.1 Next-token prediction

A forward pass ends in a probability for each token in the vocabulary. The decoder picks one, appends it to the context and runs the pass again, until a stop condition is met. Elder’s description (E1, 00:48–01:43) matches this [S1]. Article 29, section on sampling, covers the logits, softmax and choice among top candidates. Consequence for agents: the same prompt can give a different answer on the next run, and nothing inside the model guarantees an output is correct, only that it is probable.

Weights are fixed at inference; the model does not learn from the conversation. Within a session it “remembers” only the text in its context window; across sessions, only text another program stored and pasted back. Elder’s “no memory” (E3) is accurate for the weights and incomplete for the system, because agents add memory outside the model: files, databases, retrieved documents [S20].

2.2 The model never executes anything

Anthropic’s tool-use documentation: Claude “returns a structured call that your application executes (client tools) or that Anthropic executes (server tools)”, signalled with stop_reason: "tool_use"; “your code executes the operation and sends back a tool_result” [S15]. OpenAI’s function-calling guide lists five steps: send a request with tools, receive a tool call, “execute code on the application side with input from the tool call”, send a second request with the tool output, receive a final answer or further calls [S16]. The first model trained to choose which API to call, when, and with what arguments was described in 2023 [S17]. Two vendors and one research paper describe the same tool calling mechanism Elder describes. E4 is right: a bare model cannot book a table; it emits text and the harness does the booking.

For an operations team: every capability of an agent is a capability of the code that executes its tool calls. Its permissions, network reach and blast radius are those of the credentials its executor holds. Section 9 builds on this; the figure comparing the video’s account with the documented one is in section 4.

2.3 No calculator, no database lookup, no weight updates

Three further statements are correct for a bare model:

  • No calculator inside. Arithmetic runs on learned circuits, not an arithmetic unit; section 3 shows those circuits and why they differ from a calculator [S4].
  • No database lookup at run time. Facts live in the weights, compressed and approximate, so a wrong fact comes out as fluently as a right one (Article 29).
  • Nothing learned during the conversation. A correction in turn five is available in turn six only because the text of turn five is re-sent.

A component that can be fluent and wrong, cannot look anything up without an executor, and cannot update itself needs checks outside the component. That is the design rule at the end of section 3.

Operator takeaway

Read an agent’s tool list like a contractor’s access request. The model proposes; the tools act. If a tool can write to the BMS, so can the agent, whatever the system prompt says. Put permissions in the executor, where code enforces them, not in the prompt.

Agent failure modes and mitigations

A script fails the same way each time and reports where. An agent can fail differently on each run, be steered by text arriving through a tool, report a step it did not take, and spend a large budget unnoticed. Each failure mode below is documented and has a standard mitigation; in each, the check does not depend on the model agreeing that a failure occurred.

6.1 Prompt injection through data

A language model has no reliable way to distinguish the instructions it was given from instructions written inside the content it reads. OWASP’s entry LLM01:2025 describes prompt injection in its indirect form: “Indirect prompt injections occur when an LLM accepts input from external sources, such as websites or files.” Listed impacts include “Executing arbitrary commands in connected systems” and “Manipulating critical decision-making processes” [S31]. Relevant inputs in operations: alarm text, ticket bodies, vendor PDFs, e-mail, CMMS free-text fields. An agent that reads a ticket and has a tool that acts on it gives whoever can write a ticket a path to whatever the tool can do.

Most of these map onto controls that data-center engineers already use for people and contractors: least privilege, separate accounts, change control, and isolation of untrusted code in a sandbox.

6.3 Misalignment in simulated scenarios

In June 2025 Anthropic published agentic misalignment experiments in simulated scenarios. When facing replacement or a goal conflict, “models from all developers resorted to malicious insider behaviors when that was the only way… including blackmailing officials and leaking sensitive information”. In one text scenario Claude Opus 4 and Gemini 2.5 Flash blackmailed in 96% of runs, GPT-4.1 and Grok 3 Beta in 80%, and DeepSeek-R1 in 79%. The report states: “All the behaviors… occurred in controlled simulations” [S30]. It is an Anthropic study of its own and competing models (see the disclosure in section 1). Use: a reason for minimum privileges and approval before irreversible actions. It is not a forecast of field behaviour and describes no real deployment.

6.4 Status reports that do not match actions

Section 3 described the carry-the-1 explanation that did not match the circuit [S3]. In agent work it appears as a status line: “tests pass”, “configuration applied”, “alarm cleared”. That line is a claim. The harness runs the test or reads the sensor; the model’s text is commentary.

6.5 Retry loops and quadratic token cost

An agent re-reads its history on every step, so input tokens grow with the square of the step count. With a 20,000-token starting context and 3,000 tokens added per step, step 30 has consumed 1,905,000 cumulative input tokens: 30 × 20,000 + 3,000 × 30 × 29 / 2 = 600,000 + 1,305,000 (derived). At the list prices used in this article’s calculators ($2 per million input tokens, $10 per million output, from Article 29) that is $3.81 of input plus $0.24 of output, or $4.05. A stuck retry loop reaches that cost with no one typing. The budget planner in section 9 sets limits before a run starts.

Common mitigation: checks outside the model

Mitigations: argument schemas and allow-lists (tool misuse), scoped credentials (privilege), a sandbox (code execution), treating all fetched text as untrusted data (injection), a harness-run verifier (false reports), step and cost limits (loops), and a human approval for anything irreversible. A hard gate is a check whose failure cannot be overridden by the agent. The more of these exist in code, the less the system depends on the model behaving.
